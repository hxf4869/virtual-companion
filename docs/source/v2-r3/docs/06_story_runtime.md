# 三 NPC 受规则剧情：实现与验收 · R3

用户已确认 **B2：本模块属于首个完整可用版本**，不是首发后的可选任务。P0–P4 可以逐步演示，但完成 P5 三 NPC 剧情和 P6 后才达到本包首版范围。当前仅修订材料，不运行剧情或调用模型。未来在真实复杂卡、桥接和记忆基础之后开发；自由酒馆模式保留原生玩法，本模块增加有权威状态和角色知情边界的路径。剧情页面先按 [DESIGN.md](../DESIGN.md) 形成 Stitch 桌面/手机设计稿，再实现。

## 1. 第一个可玩的内容

使用原创“雨夜旅馆：失踪的怀表”：

- 玩家作为调查者进入旅馆。
- 三个NPC：老板林岚、住客周澈、修复师苏禾。
- 少量场景：大堂、厨房、维修间。
- 一份固定真相、三条关键线索、有限行动和可判定结局。
- 数据见 [rainy_inn_case.json](../fixtures/rainy_inn_case.json)。

本案是验证角色认知和规则的短案例，不要求先做开放世界、多人真人联机或无限自动剧情。

## 2. 三种不同的信息

| 层 | 内容 | 谁可读 |
|---|---|---|
| 世界真相 | 谁取走怀表、藏在哪里、真实时间线 | 规则引擎；按角色已知条件输出相关片段 |
| 角色认知 | 某角色亲眼见到、听说、误信或隐瞒什么 | 当前角色自己的view |
| 角色表达 | 回答、质疑、撒谎、提出行动 | 根据对话公开 / 私聊范围记录 |

NPC说“我没去过维修间”是陈述事件，不能直接覆盖世界中的真实行动记录。玩家猜中答案也不自动修改真相。角色可以误判，规则需要保持一致。

## 3. 最小领域模型

- WorldDefinition：故事背景、可用角色模板、初始规则和作者真相。
- WorldRun：这一局实例、当前版本、时间 / 幕、结束状态。
- Participant：玩家 / NPC实例、当前场景、目标和可用动作。
- Event：已经提交的行动或陈述、actor、visibility、来源、world_version。
- ActorView：依据公开信息和角色权限生成的可见投影。
- Branch：父分支 / 分叉点及当前有效事件范围。

尽量复用现有PG事务和任务设施；无需独立图数据库来判断“谁有钥匙”。事件不要求无限细分，能支持来源和回档即可。

## 4. 一轮交互

1. 玩家选择询问对象或提交有限行动。
2. 服务端确认当前run、actor、expected_version和场景。
3. 生成该角色可见的设定、事件、记忆与工具范围。
4. 前端在受规则剧情的上下文路径中调用ST生成能力；最终请求再次核对可见范围。
5. NPC生成台词及可选行动提议。
6. 程序检查目标、条件、物品归属和版本，通过后提交一次。
7. 把结果投影给该知道的角色与界面，必要时再唤醒一个相关NPC。

只询问A时不让B、C和导演全部调用一遍模型。可以同一模型服务、不同上下文运行三个角色，不需要三个常驻模型实例。

纯台词可以流式显示；会改变证据或物品的结果须经过规则裁决后呈现为已发生事件。不要先把“拿到了物品”作为成功正文输出，之后才发现规则拒绝。

## 5. 上下文构建与秘密隔离

ST原生群聊共享历史，直接设置多张卡不能形成严格知情隔离。普通世界书的关键词触发也不是访问控制。

受规则路径需要：

- 从Go读取ActorView，而不是全体角色和全部世界真相。
- 仅使用该run / branch / view可见的记忆。
- 区分公开群聊事件与私聊事件。
- 世界书条目带模式和角色可见规则；GM真相不放进所有人共用的卡或全局世界书。
- 工具检索与角色对话使用相同范围，不能通过原文回查工具绕过过滤。
- 只在generate_interceptor裁剪历史不够，后续世界书 / EJS / 扩展仍可能注入内容；检查真正送往模型的最终请求。

当前固定ST版本的CHAT_COMPLETION_PROMPT_READY / SETTINGS_READY是候选挂钩，执行时确认可修改语义和顺序。如果仍无法可靠控制最后请求，允许有证据的小补丁；不要“补一个不要泄密的prompt”就宣布完成。

严格模式仅对已验证的 card / provider / plugin 组合声明支持。首版三种协议 Anthropic Messages、OpenAI Chat Completions、OpenAI Responses 都必须有可运行的严格剧情基线；逐协议捕获真正出站的请求，包含工具后续轮次与协议转换后的字段。不能因最早的 ST prompt 已过滤，就跳过后置注入或 Responses 适配后的检查。

普通复杂卡可继续在自由模式使用。若某扩展会独立发起不受本模式控制的额外请求，须适配或在严格模式关闭该额外路径，并明确能力差异。验证按代表性组合覆盖已承诺路径，不建立所有模型与扩展排列组合的无穷门禁。

本目标是NPC模型只获得该有的信息，不建设防止私人作者查看自己剧本文件的系统。也不宣称能禁止模型凭推理猜中未知事实；验收重点是输入来源边界和规则结果。

首版严格剧情采用显式上下文：每个新回合从当前 ActorView 组装实际输入，不以 Responses 的 conversation / previous_response_id 等远端历史引用跨回合续接，也不复用其他角色或旧分支的不透明上下文。官方 [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state) 说明这些引用能够继承先前内容，因此只检查当前可见 payload 不足以证明隔离。

同一受控工具回合如需回传本次模型输出 / reasoning 项，限定在相同 owner、instance、run、branch、actor、config revision 与来源版本；上下文变化、取消、回档或来源移除时丢弃旧回合续接状态并重新构造。首版不建设跨回合远端会话管理器。store:false 可按供应商语义减少保存，但不能单独证明没有继承历史，也不等于删除供应商全部日志。

## 6. MVU与世界状态的关系

自由模式由卡自己的MVU / 脚本维护stat_data；Go不另行写同字段。

严格剧情由Go拥有线索、物品、真相和可见性。状态面板获取当前actor view，MVU可作为显示投影或处理另一个明确的非权威命名空间。若通过卡按钮修改世界，必须发Action Command并经过校验，不能直接改面板数字当作服务端事实。

不要把完整GM状态复制进浏览器角色变量，再寄希望于提示词不读取。只向角色上下文通道提供所需投影；作者调试入口与模型输入明确分开。

## 7. 动作与幂等

P5交付的动作可以限定为：询问、查看场景、展示线索、请求物品、指认。

每个修改命令带稳定 action_id 和 expected_world_version。ST 聊天保存还须带 F2 的 expected_chat_revision，世界版本和聊天版本是不同对象，不能互相替代。相同action_id重试返回已提交结果；状态版本变化时重新检查条件。对同一world run的修改先顺序处理，不引入多进程并发世界模拟。

世界事件提交与 ST 聊天保存是两个完成状态。Go 在提交世界事件时用同一已有 PG 事务记录待投影状态，以 world_event_id 作为幂等键。若 ST 保存冲突或浏览器在两者之间关闭，世界动作保留已提交结果；重新加载当前 chat revision 后只补写同一结果投影，不再次转移物品、推进回合或让模型重新执行行动。

界面可显示“行动已生效，聊天记录待同步”；若读取 ST 已存在该 world_event_id，则补确认而非重复追加。回档 / 分支失效时取消未完成的旧投影；用户主动删除已经存在的投影不自动补回。删除一条显示消息不等于撤销世界动作。复用既有任务和版本保护即可，不新增跨系统事务平台。

模型可产生格式错误或无效动作，执行器返回明确结果并在有限步数内收敛。未支持动作不能无限让模型自我修正。

## 8. 分支与回档

分支记录分叉点。当前世界状态和ActorView来自有效分支事件；父分支可见前缀可继承，分叉后的互斥事件不能混入。

回档后：

- 物品、线索、场景和角色认知一致恢复。
- 相关记忆 / 摘要按当前branch重建或失效。
- 旧分支后台任务提交时检查branch和revision，不能继续改当前世界。
- 重新生成台词不自动重复提交同一个行动。

ST的聊天分支与Go WorldRun分支需要显式映射，不通过两个同名字符串碰巧相同来推断关联。

## 9. 同长期陪伴的联系

长期陪伴角色可进入剧情实例；本局身份、秘密和行动留在该run。结局后生成“我们一起玩过这局”的共同经历摘要，允许用户选择保存。默认不把扮演职业、隐瞒和犯罪剧情转成现实用户事实。

首个短案例先用独立原创NPC完成；P5 的 W14 再实现最小跨模块路径：让一位已有陪伴角色扮演三个NPC之一，建立独立 run / branch 实例映射，结束后给出候选共同游玩摘要，用户选择是否保存。不增加第四个必需Agent，也不作为P1复杂卡验收前置。S05验证拒绝保存时日常记忆不变，选择保存时只写入明确的共同游玩经历。

## 10. 必须验证的案例

1. A的最终请求不包含B私聊线索或GM唯一测试标记。
2. 世界书、摘要、向量召回和后置脚本都经过最后请求检查。
3. NPC谎言作为陈述保存，不能修改真相。
4. 未取得钥匙不能完成需要钥匙的检查；合法路径能解锁。
5. 同一动作重试不会重复转移物品或推进回合；世界提交后 ST 保存冲突 / 崩溃只重试投影，确认丢失时读回查重。
6. 回档后角色不再知道未来线索，旧异步任务和远端续接上下文无法写回或继承。
7. 三协议各以固定 provider 验证最终出站上下文、流/工具结果和规则提交；确定性走到结局。实际模型在已配置用途和费用额度内完成代表性问答，单独记录，不把固定输出当成真实模型效果。
8. 只唤醒必要角色，存在最大回合 / 自动回复上限与停止按钮。

仅检查“NPC没把秘密说出来”不充分。测试应捕获最终请求、可见条目ID和提交的事件；唯一测试标记用于发现路径泄漏，不能替代对语义内容与来源的检查。

P5 沿用 C1 存储保护、F2 全部聊天保存版本检查、来源对账、跨域导出删除和 G2 用途绑定/费用边界。剧情导演与 NPC 可以复用同一已配置模型，也可以独立选择；只在需要时调用相关角色，不为每个 NPC 建常驻模型进程。

E3 不迁移旧聊天，旧聊天派生的记忆默认不进入新剧情上下文；新入局角色只使用本轮允许的角色设定与明确可见记忆。剧情通知若启用，使用已选择的邮箱/飞书渠道，发送必要提示而不泄露其他角色私密线索。外部通知成功不代表剧情动作或 ST 消息已经提交。
