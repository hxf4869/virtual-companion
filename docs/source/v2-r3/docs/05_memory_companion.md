# 长期记忆、关系与主动陪伴实施要求 · R3

本专题在 P2 来源闭环成立后进入 P3/P4。当前 R3 仅修订材料，未启动实施。A1、B2、C1、D2（邮箱＋飞书）、E3、F2、G2 已确认；具体模型、凭据和费用额度为运行前配置。界面及复杂卡前台运行使用原生 ST；本模块负责跨会话记忆和服务器任务，按 [DESIGN.md](../DESIGN.md) 设计记忆和通知页面。

## 1. 用户应获得的体验

- 多个角色分别记住自己与用户的经历，创建同款卡不会共享私人记忆。
- 近期和长期相关事情能在新会话中找回，用户不必每次复述。
- 用户说“我已经搬到上海”，当前事实不再继续使用旧城市。
- 能打开记忆面板看到保存内容、来源和时间，修改或删除。
- 角色根据待跟进事项在合适时机问候；没有值得说的事可以保持沉默。
- 剧情里的身份和事件不会自动变成现实用户画像。

“养成”先通过共同经历、理解变化和互动习惯体现。核心角色设定由作者 / 用户控制，不让后台画像随意覆盖人设。可以记录熟悉程度、信任等少量关系状态，但不把首版变成复杂数值游戏。

## 2. 数据分类和权威边界

| 类型 | 内容 | 处理 |
|---|---|---|
| 核心角色设定 | 人设、生平、语言风格 | ST卡版本快照；不能由自动提炼覆盖 |
| 明确事实 / 偏好 | 用户当前城市、喜欢的交流方式 | 有来源、有时间，可更正和替代 |
| 共同经历 | 讨论、计划和一起完成的活动 | 事件摘要加原始来源，不把一句模型想象当发生事实 |
| 目标 / 承诺 / 跟进 | 面试、待办、承诺、提醒 | Go结构化状态，实际完成由结果事件证明 |
| 会话摘要 | 最近话题、未完成讨论 | 按来源范围和分支更新，过时可重建 |
| 剧情认知 | 角色看见、听说、相信或隐瞒什么 | 独立world/run/branch/view，不能默认与日常共享 |

最小记忆记录需要：稳定ID、type、内容、owner、character_instance、模式、可选world_run/branch、source_refs、发生时间、状态、修订关系。具体表和模块按评估复用或重构，不必为每种类型创建独立服务，也不为已经退役的前台保留另一套记忆接口。

已执行成功的动作来自工具 / 规则事件。assistant 说“已设置提醒”只是一句台词，不能绕过工具结果创建完成事实。

## 3. 作用域先过滤再检索

服务端根据可信身份和绑定计算范围。普通陪伴使用 owner + character_instance；剧情再加入 world_run + branch + 角色视角。模板ID、角色名、聊天数组下标不能替代实例ID。

顺序：

1. 确定owner、当前实例、模式、分支和允许共享范围。
2. 在该范围内进行关键词/向量候选检索，并取得拟使用摘要/画像的来源依赖。
3. 按来源chat去重批量读回当前持久状态，包含未重新打开的旧chat；剔除旧修订并失效派生项，必要时重做一次有界召回。
4. 对核验有效的候选排序、去重、预算裁剪；摘要同样只能使用已核验依赖。
5. 把内容作为有来源的历史资料注入，不作为最高优先级系统指令；最终组装检测到修订变化时重新核对或剔除。

不能先跨用户 / 跨角色查询全库，再希望模型不要泄漏。共享用户偏好必须是明确的可选产品行为；默认不把一个角色的共同经历广播给所有角色。

剧情退出后只允许用户选定的共同游玩摘要进入日常记忆，不能自动导入凶手秘密、虚构职业或完整世界书。

E3 不迁移旧聊天。V2 从新来源建立记忆；旧来源派生的摘要、画像或记忆不因复用数据库就自动有效。若之后明确接入某项旧记忆，先核验其来源可访问性、归属、修订和删除状态；不能核验时保持不参与召回，同时保留旧数据本身的导出/删除责任。

## 4. 来源、编辑、swipe 与分支

以 [架构文档](03_architecture.md) 中已保存来源为输入。来源键至少区分chat、消息稳定ID、当前swipe、branch、内容修订。

- 未保存、取消和未选择的候选回复不能成为当前有效共同经历。
- 用户编辑后，旧来源的派生事实失效或被替代；后台任务提交前复核来源修订。
- 用户删除后，删除标记 / 版本号应阻止已经排队的旧任务复活记忆。
- 切换swipe或回档后，根据当前有效分支重新选来源；不要把两条互斥路线同时放入上下文。
- 摘要、画像、向量和图节点均为来源派生项，遗忘不能只删除一个列表行。
- 若外部引擎无法精确删除某个衍生项，可在本应用层先屏蔽来源并重建该范围；不能宣称物理删除已经完成。

保存事件只用于加速，不能作为唯一可靠性来源。浏览器在保存编辑/删除后、通知Go前关闭时，打开/重连、候选检索、后台生成/提取提交均通过ST服务端读回恢复；先失效旧来源和派生摘要，再异步重建。暂时读错不当删除，未核验的旧内容不注入。具体顺序见架构第12节。

不建立全局事件溯源平台。复用现有来源/生命周期字段、少量修订索引与可重建摘要即可。

## 5. 召回实现与基线

现有早期固定20条路径必须被正式ST请求使用的共享 MemoryService 替换。

查询由当前用户输入和少量近期有效对话构成；先作用域过滤，再召回。建议已有PG / pgvector建立关键词与向量混合候选；中文分词 / 字符匹配策略需要真实中文样例验证，不能直接假定英文全文配置适用。

不自行实现embedding模型、ANN索引或图数据库。使用已有库、数据库能力或选定记忆引擎。在线query embedding可能仍有耗时，应设独立预算和超时；索引构建与大批提炼放后台。

排序先考虑相关性，再结合当前有效状态、事件时间与用户明确重要性；不把全部旧信息仅按最近访问次数强化。记录实际入选来源，便于解释错误。

上下文组合采用ST原生扩展注入点。新增记忆有独立名称、可关闭和预算，不覆盖卡自己的system prompt、世界书和后置指令。常驻短摘要只在有意义更新时变化，临时相关记忆按话题变化；是否缓存受模型供应商规则影响，不承诺固定缓存命中率。

当普通陪伴检索失败，可使用当前已核验的卡与对话继续并说明跳过了长期记忆；只有来源仍有效且已核对的短摘要才能使用，不能拿可能已删除的旧摘要兜底。严格剧情不能因此回退到包含全局秘密的共享上下文。

## 6. MemoryCore：首个外部候选，不强制入主链

固定研究版本：TencentCloud/TencentDB-Agent-Memory，084bed45cad6bb7f877455082cee82835d65671a，当前默认分支 feat/server_team，MIT。

已核查能力：

- L0原始对话、L1原子记忆、L2场景、L3核心画像。
- 更新、合并、删除和全资产清理接口。
- 本地SQLite + sqlite-vec + FTS5，腾讯云后端是可选。
- 抽取链包括模型抽取、候选检索、模型去重决策和写入，不能全部放到首字等待路径。

重要适配：

1. [profile-scope.ts](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/084bed45cad6bb7f877455082cee82835d65671a/MemoryCore/src/core/profile/profile-scope.ts) 的L2/L3按team-or-user + agent汇总，有team时有意忽略user/session。为本产品映射独立owner命名空间和CharacterInstance，不能全平台共用team+模板agent。
2. [l1-extractor.ts](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/084bed45cad6bb7f877455082cee82835d65671a/MemoryCore/src/core/record/l1-extractor.ts) 去重filter包含sessionId。必须验证跨会话更正，必要时由业务层维护少量当前事实槽位及有效时间。
3. L3“核心”是该引擎的记忆层，不自动等于可修改作者角色卡的授权。
4. 全量清理存在，不应写成“不支持删除”；单条遗忘能否清除所有衍生画像要实测。

参考：[v3 API](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/084bed45cad6bb7f877455082cee82835d65671a/MemoryCore/v3-api-memorycore-doc.md)、[存储工厂](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/084bed45cad6bb7f877455082cee82835d65671a/MemoryCore/src/core/store/factory.ts)。

接入默认通过显式HTTP API或受控TS模块，不用透明Proxy捕获所有模式并自动混合记忆。只部署所需MemoryCore路径，不把Hub/Panel/CodeGraph/Wiki一起作为前置平台。

用同一组中文fixtures对照已有基线：作用域、改口、删除、分支和延迟。能减少自研并通过关键用例则采用；否则记录具体缺口，继续用已有存储完善检索。两个方案不长期并行写生产数据；对照期使用隔离合成数据。正式路径还须满足 C1 的保护清单，以及跨域导出/删除、来源核对、备份恢复要求。只有Go记录删除而引擎派生数据仍在，不能报告全部删除。

如果采用MemoryCore，Go保留权威来源 / 纠正 / 作用域 / 任务；该引擎承担明确的提取与检索职责。关闭旧重复提取任务或改为调用适配器，避免双画像。

## 8. 主动陪伴的最小闭环

先支持一个可解释场景：“用户说明明天有面试，角色记下待跟进事项，事情结束后的合适时段问结果；用户提前说过结果则取消追问。”

建议数据：

- FollowUp：目标角色、来源、主题、来源时间/时区、规范化事件日期/时间及精度、提醒时间、状态、取消条件；歧义保持待澄清。
- ProactivePolicy：开关、quiet hours、每日上限、最近互动、允许模式。
- InboxItem：稳定event_id、目标实例/chat/branch、来源revision、内容或意图、交付状态、已保存message/revision、当前链接状态；delivered与当前消息仍存在分开。

优先复用现有持久任务和有限重试；如其实现阻碍本版要求，允许在 Go 内重构，不另建没有实际必要的 RabbitMQ / Redis 队列。每个实例同一时刻合并同类待整理任务，控制后台并发，普通聊天不等待提炼完成。

主动流程：

1. 从已保存且经当前来源核对的消息建立跟进，按来源时间和当时时区规范化日期；不在任务重试时重算。
2. 到期先检查用户设置、时区、话题是否已解决、是否已问过、会话是否改变。
3. 没有足够理由则保持沉默 / 延后，不为了完成任务强行问候。
4. server companion profile生成普通内容，或为复杂脚本卡保存waiting-host意图。
5. 入inbox；浏览器上线后校验目标chat / branch / revision，过期内容取消或重新规划。
6. 领取交付权后仍须满足 F2 全聊天保存版本检查，通过原生路径保存inbox_event_id与消息身份，再读回保存版本后ACK。写入后ACK前崩溃先查重。手机已ACK后电脑旧快照也必须被服务端拒绝；用户主动删除/回档则更新当前链接状态，不自动补投。

D2 已确认，首版同时交付**邮箱和飞书**两种可配置通知渠道。工程默认使用 SMTP 邮件与[飞书群自定义机器人 Webhook](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN)；渠道接收对象、凭据和预览内容在设置中填写，不需要现在提供。用户可按角色/事件选择启用哪一渠道，不能把支持两渠道理解为每条消息都强制双发。

通知在 inbox 或 waiting-host 意图持久化后进入持久投递任务。ready 内容可提示“有一条新消息”；waiting-host 只能如实提示“有待继续的互动”，不能声称复杂卡已经离线生成回复。通知带返回对应会话的链接，接收平台内继续聊天不属于本版通知功能。

inbox 保存、ST 消息保存、平台接受、实际手机显示和用户已读分别记状态。邮件 SMTP 接收或飞书成功响应不证明手机已弹出通知；两渠道都须在目标手机关闭网页后实际观察，拒收、权限关闭和客户端免打扰按实况记录。通知失败独立重试，不回滚已存在的 inbox，也不以发送成功替代 ST 保存 ACK。

每个 event＋渠道＋目标有唯一业务投递身份，重试退避且有上限。网络在平台接收后超时属于结果未知；平台不能按幂等键保证时，要承认可能重复，不假称外部投递恰好一次。过期、取消、已解决及用户删除后的待发送任务重新检查后停止；已经送到外部客户端的通知不承诺撤回。默认发送必要提示和链接，明确飞书群成员可见范围，内容预览由配置控制。

微信、企业微信、QQ 为后续候选，不写空适配器、预占队列或把它们列为首版验收。首版不另外强制开发 Web Push。

默认由用户为每个角色显式启用主动互动，避免导入任意社区卡就自动开始后台运行。对复杂卡把离线能力写清楚，不静默降级。

## 9. 必要工具范围

P4优先完成“查询自己的待跟进事项 / 创建可取消的应用内提醒”之一。工具完成事件有ID、实际结果和来源；模型台词不能替代成功结果。

工具调用有单轮最大步数、超时和重复调用抑制；数值按所选实现配置并记录。读工具可并行；修改同一关系 / 世界状态的动作按当前版本校验。无需第一版开放任意shell、任意文件写入或全部MCP工具。

## 10. 验收

使用 [memory_cases.json](../fixtures/memory_cases.json) 的M01–M12，以及 [lifecycle_cases.json](../fixtures/lifecycle_cases.json)：

- 超过20条有效记忆后，相关的新信息仍能召回。
- 同款角色、不同用户、同一用户不同实例不会串记忆。
- 跨会话更正优先当前事实，旧事实可作为过去经历。
- 遗忘后列表、检索、摘要 / 画像和旧后台任务都不复活。
- 未选择swipe / 废弃branch不进入当前事实。
- 用户角色扮演的虚构身份不进入现实画像。
- 关闭页面后支持的服务端任务完成，复杂脚本任务明确等待宿主。
- ST保存失败不能把inbox标为delivered。
- 所有验收检查实际模型请求和持久状态，不只看记忆列表出现一条记录。
- 明确日期不漂移，来源与查询的相对词各用自己的时间基准；歧义不创建可触发提醒。
- 原文、长期记忆、模型上下文与备份删除各自有真实完成语义。
- G2 各用途绑定和配置 revision 明确；实际模型/用途/预算尚未配置时不发真实调用。
- 邮箱与飞书均完成关闭网页后的实际接收测试；平台已接受、手机已显示与已读不混淆。


## 11. 时间规范化：来源与查询分别解释

保存source_timestamp、source_timezone、原始时间表达、解释规则和规范化event_date/event_time/timezone；recorded_at或提取执行时间单独记录。提醒使用独立reminder_at或明确已确认规则，不能把只有日期的事件擅自变成零点提醒。

本包M11明确采用周一开始的下一自然周：2026-10-20（Asia/Shanghai）说“下周五”，指2026-10-30；2026-10-27问“下周五”，指2026-11-06。检索不应把10/30婚礼挪到11/06。M01直接使用10/30，避免用例自身含混。

真实语言有歧义、来源时区缺失或日期无法确定时保留needs_clarification，说明可能解释，不设置可触发提醒、不改已有计划。抽取延迟、重试、服务器时区变化或用户后来换时区，不重新解释旧表达；用户明确改期则建立新修订并取消旧跟进。跨时区显示可以转换已知瞬时，但不能把仅有当地日期的事件伪装为精确瞬时。

## 12. 遗忘按钮的准确语义

“删除这条长期记忆”撤销记忆及其派生摘要/画像，保留必要来源抑制以阻止旧任务重新提取；ST原文仍在当前历史时，仍可能用于回复。按钮说明必须明确这一点。

“删除聊天及其派生记忆”处理选定原文与来源，展示是否包括分支、副本和在线备份；离线备份按明确期限处理。“后续回复不再使用这些记录”只有在历史、召回、摘要、工具和目标插件最终请求都适配后才能提供。未实现该排除能力时，不承诺模型不会再看到。

这些功能和删号均复用架构第16节的跨域编排。不能因为MemoryCore列表中记录不见了就宣布Go/ST/备份全部清除。

## 13. 模型、配置和预算

G2 已确认：前台聊天、提取/去重/摘要、后台问候、剧情导演/NPC 和需要时的 embedding 分别固定绑定用途 profile，统一入口展示实际 provider、model、协议和 config_revision。前台从模型 A 改为 B，不自动改变独立绑定的后台 A；这是预期行为，界面须清楚展示，不能误报为配置漂移。首版不需要为已放弃的 G1 再建设自动跟随模式。

直接从 ST 原生入口修改当前聊天配置也要与统一管理入口核对。修改共享 provider 的 endpoint/key 或删除被引用的 profile 会影响所有引用用途，应展示引用范围并按配置版本处理；只有受影响且未同步的用途暂停。排队任务在实际开始时解析自己绑定的最新有效配置，运行中的单次 run 保持不可变快照；凭据撤销仍能阻断后续请求。

三种聊天协议为 Anthropic Messages、OpenAI Chat Completions、OpenAI Responses；自定义 URL、API Key、模型 ID、上下文和输出限制在统一页面配置。Embedding 使用明确的独立接口与模型，不能把聊天协议选择当成 embedding 支持。缺少真实配置时固定 provider 仍可验证流程，不以此阻塞需求包或独立开发。

具体 provider/model、真实验收总预算和日常后台预算仍待运行配置，G2 本身不授权新增费用。预算覆盖重试、MVU 额外请求和选定记忆引擎内部调用；价格/计费边界不清楚不自行发起付费请求。新候选配置不自动增加允许向其发送的数据用途。详细机制见架构第17节，验收见 [验收与运行](08_verification_operations.md)。
