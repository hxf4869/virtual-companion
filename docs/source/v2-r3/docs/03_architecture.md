本轮仅修订材料，不启动项目代码、服务、模型调用或部署。具体模型、密钥、真实验收预算、通知接收对象和备份策略值属于运行配置，未填写不阻塞需求包；也不构成真实运行或费用授权。所有新增技术风险是静态依据或设计缺口，应用运行状态仍为 NOT_RUN。

## 3. 模块职责与权威数据

| 模块 | 独占负责 | 实现边界 |
|---|---|---|
| SillyTavern + 原生前端 | 卡、世界书、预设、聊天原文、swipe、群聊、前台 prompt 构建、复杂卡脚本生命周期、前台生成链 | ST 作为主产品宿主；Go 不为同一前台回合生成第二份回复 |
| 自有 UI extension | 按统一设计规范实现角色 / 记忆 / 剧情 / 模型 / 通知页面、上下文注入、来源事件采集、inbox 展示与导入 | 复用 ST 上下文与组件，不维护第二份可独立编辑的聊天数据库 |
| 自有 server plugin | 同源 API、已认证 ST 用户映射、读取已保存聊天、F2 保存适配、内部 Go 桥接 | 不信任浏览器任意 owner_id，不直接写 PG 业务表；原生入口覆盖不了时用集中小补丁 |
| Go companion service | 角色实例、关系、长期记忆、持久任务、跟进 / inbox、通知投递、严格剧情状态、模型用途绑定与预算 | 可彻底重构旧模块；不直接修改 ST JSONL，不重复构造自由复杂卡前台 prompt |
| PostgreSQL | Go 领域状态、任务、来源快照、可重建记忆视图、通知记录与模型登记 | 不成为 ST 原文的第二个可独立编辑主库 |

V2 原始聊天以 ST 为权威；Go 保留的来源快照、索引和修订关系由 ST 已保存状态更新。Go 关系 / 提醒 / 故事规则状态以 PG 为权威，界面通过领域 API 发起变更。旧 Go 原文按 E3 保留在原数据域或受保护归档中，不复制到 ST；其数据权利职责见第 13、16 节。

保留密码＋TOTP 的用户可见认证要求，优先利用现有 Go 能力；实现质量不足时可重构认证模块。受控反向代理把已验证 owner 映射到 ST 账号并建立 ST 会话。Go 内部业务 API 使用受限桥接凭据和服务端用户映射；保留必要账号身份关联以处理既有数据。一次可见登录与完整边界按第 14 节验证，保留旧源码本身不算验收。

模型采用一个逻辑登记和明确的运行投影：统一入口管理供应商 / 模型 / 用途绑定，Go 管登记版本及预算，ST 仍执行其原生前台配置。直接修改原生 ST 设置须反映到登记或显式标为待同步，不能形成同用途的两份独立配置。每次 run 记录实际生效配置，详见第 17 节。

普通前台聊天由 ST 完成一次生成链；记忆提炼、提醒 / 跟进和剧情规则各有明确单一执行者。ST、Go、Pi 不同时接管同一任务。

## 4. 扩展优先，小补丁有明确触发条件

`getContext()` 已提供 `setExtensionPrompt`、`saveChat`、`reloadCurrentChat`、`generate`、消息事件等能力；server plugin 可创建 `/api/plugins/{id}/*` 路由。服务器插件在当前固定版本位于登录和 CSRF 中间件之后，可从 `req.user.profile.handle` 等服务端信息建立映射。但默认用户上下文本身不证明访问者已经通过认证，必须同时满足第 14 节的完整入口边界。

推荐自有代码放在现有仓库的 `integrations/sillytavern-extension`、`integrations/sillytavern-server-plugin` 等明确目录；上游作为固定版本依赖构建或挂载。记录 upstream commit、插件 commit、构建步骤、必要补丁列表。不要复制巨大上游代码后混入自己的主业务又失去来源关系。

只在以下具体缺口不能用公开接口解决时创建小补丁：

1. 可靠的聊天持久化完成事件，以及 F2 对全部受支持写入路径的版本保护。
2. 受规则剧情的最后一层请求构造 / 审计入口。
3. 经过最小复现证明的目标插件兼容问题。
4. 认证映射后的 ST 会话绑定检查，若公开扩展无法覆盖原生资源和业务路由。
5. 三协议中原生宿主缺少的请求 / 流式适配；先复用已有成熟实现，不为已支持的原生路径另写一套生成器。C1 已选，本版不实施 ST 全面应用层加密改造。

每个补丁附理由、所需上游版本和可去除条件。不要求执行 Agent 为每个小改动申请批准。

## 5. 浏览器生成、服务器常驻与首版通知

官方 UI 扩展在浏览器中运行，常依赖 DOM、SillyTavern 上下文和事件。实际 `Generate()`、世界书 / 宏 / 正则处理也主要位于浏览器代码。启动 Node ST 服务不能让所有前端脚本在浏览器关闭后继续执行。

主动陪伴采用两个明确能力级别：

- **服务端可运行的 companion profile**：用已映射的人设版本、核验后的长期记忆和待跟进事项生成普通陪伴消息，存入 Go inbox。无浏览器时仍能调度和生成；上线后通过真实 ST 宿主导入对应聊天。
- **依赖复杂卡脚本的自动续写**：记录 waiting-host 意图，在打开对应聊天且原生运行环境可用后执行。首版不引入无头浏览器集群，也不宣称离线维持所有 MVU / 酒馆助手行为。

主动消息有稳定 event_id、目标角色 / 会话、due time、quiet hours、过期和重复抑制。Go 生成内容不代表已进入 ST 原文；必须在 F2 保护路径保存并确认后才标记 ST delivered，并维护当前消息链接状态。inbox 是交付事件，不是另一份权威聊天。

### 5.1 已确认邮箱＋飞书；协议形式由工程实现

首版两个渠道都需要完成实现及对应实际接收验证。工程默认采用 **SMTP 邮件＋飞书自定义机器人群 Webhook**，复用现有邮件能力、成熟 SMTP 库和官方 Webhook 协议；这是工程方案，不是用户指定了具体邮箱服务商或飞书群。若目标账号条件更适合飞书应用消息，可在同一渠道范围内采用成熟官方实现，并记录其接收范围。不要因此引入第二套聊天、记忆或模型平台。

每个渠道配置启停、接收目标、凭据引用、可通知的角色 / 事件类型、静默时间和频率；接收地址 / 群及是否允许内容预览由运行设置明确。默认通知为简短提示和受认证保护的会话 / inbox 链接，群通知不能默认携带私密聊天全文。链接不包含 API Key、消息全文或可长期绕过登录的令牌。

SMTP 配置包括 host、port、TLS 方式、发件身份和认证引用；复用成熟实现的校验和连接处理，不能因测试便利关闭证书校验。飞书保存 Webhook 和实际启用的签名配置，日志脱敏；HTTP 成功与业务返回成功分别检查。配置保存本身不发送测试消息；测试按钮在用户配置明确的目标上执行，不向猜测的地址或群发送。当前包不发邮件或平台消息，也不开通收费服务。

微信、企业微信、QQ 等是后续候选。首版不安装其协议客户端、不注册占位插件、不为它们建设通用适配平台。浏览器 Web Push 不是本次另一个必做渠道；D2 由所选邮箱 / 飞书客户端的实际手机接收体验验收。

### 5.2 一个事件、多渠道状态与失败语义

同一主动事件可产生 email 和 feishu 两条投递记录，以 `(event_id, channel, configured_target)` 防止本应用重复创建任务。渠道独立重试和退避，任务复用 Go 既有持久执行机制；不新增消息中台。

| 状态域 | 代表的事实 |
|---|---|
| inbox 已生成 | 主动内容已在 Go 持久化，可等待 ST 宿主或用户查看 |
| ST delivered | 已通过 F2 保存并读回确认到指定聊天；手机通知成功不能代替它 |
| 渠道 accepted | SMTP 服务或飞书接口确认接受 / 成功；不等于邮件已进收件箱或手机已显示 |
| 渠道 failed / unknown | 已知拒绝或发送结果不确定；分别记录原因，不能一律声称未发送并无限重试 |
| 手机展示 / 人工验收 | 在声明支持的目标手机、客户端和权限条件下实际观察到提醒 |
| 应用内已读 | 用户在本产品读过事件；不因渠道 accepted 自动标已读 |

SMTP 的 Message-ID、飞书请求关联 ID 和本地去重不能凭空提供远端 exactly-once。网络在服务接收后断开时，记录 delivery_unknown；采用有限重试 / 明确的再次发送操作并说明可能重复，不把结果不确定当作无成本无限重发。重复投递不会再生成一条新的 AI 内容或重复向 ST 追加消息。

通知可以先于用户打开 ST 发生；点击后进入该角色的 inbox 或真实已存在的消息。waiting-host 意图只能显示“有待继续的互动”，不能把尚未执行的复杂卡续写伪装成已生成回复。过期、取消、用户删除和静默策略须检查于实际发送前。目标手机的系统通知权限、免打扰和邮件客户端同步条件记录为运行环境条件；接口成功不能据此填“终端送达 PASS”。

依据：[飞书自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN)。

## 6. 原生保存边界与多设备策略 F2（已确认）

以下是静态源码事实和由此识别的设计风险；本次没有运行复现应用故障，修订后的机制也尚未运行验证。

- `MESSAGE_RECEIVED` 代表消息进入浏览器对象，不等于服务器已保存；`saveChatConditional()` 会捕获保存错误，单独 await 不能作为持久化成功证据。
- 固定 ST 的单聊 `/save` 与 `/group/save` 经 `trySaveChat()` 保存完整 chat 数组；`checkChatIntegrity()` 比较 header 的 integrity slug，`force` 可跳过原生检查，不能当每次修订的版本冲突控制。
- 删除、群聊删除、重命名和导入另有写入路径，仅保护 inbox 或 `trySaveChat()` 不覆盖全部变更。
- 原生 `getChatData()` 的空数组可能来自缺失或读取失败；不能直接认定用户删除了所有来源。
- 当前服务端没有可直接复用的 chat_saved 事件；保存通知仍需适配或最小补丁。

具体风险是：手机写入主动消息并 ACK 后，电脑仍持有不含该消息的旧完整快照。若允许覆盖保存，Go delivered 会与当前内容脱节。投递租约、event_id 查重、ACK 前读回都不能独立阻止这个后续保存者。

**用户已选 F2：两端可编辑，全部保存带读取基线版本，过期提交由服务端拒绝。** 不再实施 F1 产品模式，不建设 CRDT / OT 或通用多人协作系统。

### 6.1 全部受支持写入路径统一保护

覆盖新消息、普通编辑、元数据 / 脚本自动保存、重生成和 swipe、删消息、整个 chat 删除、重命名、分支 / 回档、覆盖导入及群聊对应路径。新分支获得独立 chat identity，创建时验证父聊天读取基线。原生 `force` 不得绕过本项目版本检查。

按固定版本盘点入口，尽量集中适配；公开扩展无法覆盖原生入口时，允许有记录的最小上游保存补丁。首版单 ST Node 实例可在该实例内按稳定 chat identity 串行执行“校验→写入→推进版本”，不新增分布式锁。直接手改 JSONL、未适配插件绕过宿主写文件不属于支持入口；未来多个 Node 写同一卷时重新验证该边界。

### 6.2 读取基线、同端异步保存和冲突体验

读取返回持久 revision。expected revision 来自**产生该编辑快照时的读取结果**；禁止临提交查询最新 revision 再贴到旧完整快照上。对同一 base revision 的并发保存，只允许一个成功，另一方返回明确冲突。

同一标签页也不能并行发送多个旧完整快照。保存按实际修订顺序排队；异步脚本回调携带来源 chat、swipe 和基线 revision，过时结果拒绝或从当前状态重新计算。不能给旧快照换一个新 revision 强行保存。

冲突后保留本地输入和必要草稿，显示服务器已变化与重新加载入口；重新加载最新持久状态后由用户重新应用必要编辑。不盲合并 MVU、swipe、全量聊天快照或剧情世界状态，也不显示虚假“保存成功”。复杂卡自动保存冲突须显式暴露，不允许后台静默丢弃用户编辑。

### 6.3 原子提交、删除和恢复

服务器在同一 chat 临界区内完成版本比较与持久化，不能先检查、释放保护，再覆盖文件。revision 与内容一起原子保存；可在自有 header 命名空间保存 revision 并随 JSONL 原子替换，具体按固定版本文件保存方式验证。进程重启后必须从持久内容恢复 revision，内存计数器不作权威。

删除 / 重建不复用能让旧请求匹配的身份或版本；删除后的旧请求不能重建同一 chat。重命名保持 identity，锁与版本不能只按文件路径关联。对删除、重命名、覆盖导入等非单文件替换路径，要定义持久结果和重启恢复顺序；使用最小身份 / 删除状态记录即可，不扩建事件溯源平台。

W05 建立并验证 F2 全写入基础；W06 在此基础上实现来源恢复；W10 才能依赖该边界声明 inbox 可靠交付。新机制当前均待实现、待运行。

依据：[固定 chats.js](https://github.com/SillyTavern/SillyTavern/blob/7e8663cd9c184a550b37238218bdd32c6efc68e9/src/endpoints/chats.js)、[服务端插件范围](https://docs.sillytavern.app/for-contributors/server-plugins/)。

## 7. MVU 与故事规则的所有权

本节是 B2 已确认的首版 P5 要求，必须和陪伴 / 复杂卡能力一起完成对应验收。

- 自由酒馆 / 复杂卡模式：ST 与卡指定的 MVU / 脚本负责其 `stat_data` 等变量。Go 只在授权范围观察、整理记忆，不擅自同时修改这些字段。
- 受规则剧情模式：Go world state 是权威。状态栏通过受控适配器读取投影；MVU 只负责显示字段或另一个明确命名空间，不覆盖世界真相、证据权限、线索归属。
- 不对任意复杂卡同时承诺严格秘密隔离。把受规则剧情支持的卡和插件组合列入兼容矩阵；自由 RP 可以继续保留原始脚本行为。

ST 群聊默认共享历史。剧情秘密必须经独立 story-aware 上下文路径选择可见事件，不能仅向共享 prompt 添加一句“不要泄密”。

还有一个关键顺序：当前 `generate_interceptor` 在 `public/script.js` 约 4564 行运行；世界书注入在约 4623 行之后。只在 interceptor 删掉历史秘密，不足以保证世界书 / 其他插件后续不重新加入。应对最终请求进行角色可见性验证，必要时采用最小补丁。`CHAT_COMPLETION_PROMPT_READY` 和 `CHAT_COMPLETION_SETTINGS_READY` 是实际存在的候选挂钩，需按固定版本确认参数修改语义和最后执行顺序。

目标是 NPC 模型收到正确的信息视图；非商业自用场景下无需把它夸大成防作者读取自己剧本源码的权限系统。

## 11. 桥接接口与 inbox 交付语义

以下是需要实现的操作，不是声称 ST 已存在这些 API。执行时按现有路由规范命名；UI 经 `/api/plugins/companion-v2/` 等同源入口访问，Go 业务接口仅在内部提供。所有受支持写入采用已确认 F2。

| 操作 | 输入核心 | 返回 / 副作用 |
|---|---|---|
| 解析角色绑定 | 当前卡、chat、模式；身份由服务端补充 | 稳定 CharacterInstance / ConversationBinding |
| 读取/提交修订（F2） | chat、读取时的 base revision、编辑快照 | 原子拒绝旧写或返回新持久 revision；不是自动合并 |
| 核对持久来源 | 稳定 chat identity、已应用 revision、所需来源 ID | 区分成功快照、确认删除、重命名和读取暂不可用；返回差异依据 |
| 准备记忆上下文 | 当前问题、近期有效消息、实例/branch、预算 | 核对候选及汇总依赖来源后返回有效片段、revision、降级原因 |
| 确认来源修订 | chat、稳定消息 ID、swipe、内容 hash、持久化依据 | 幂等对账，先失效旧派生项，再排后台整理 |
| 管理记忆 | 查询、纠正、遗忘及操作范围 | 按相应数据权利语义修改；不能把长期记忆删除等同于聊天原文删除 |
| 领取/确认 inbox | event_id、目标实例/chat、领取令牌、保存来源与 revision | 经 F2 写入，读回确认后记录交付；重试关联已有消息 |
| 剧情视图/行动 | run、actor、expected_version、action | 可见视图；校验后提交一次规则变化 |

浏览器不提供可信 owner_id；server plugin 从通过认证边界校验的 ST 用户映射 owner 后调用 Go。内部凭据不打包到前端，保留 owner 隔离要求并优先复用 Go owner/RLS 能力。无浏览器时，Go 后台也应通过受限内部桥接核对 ST 来源，不能跳过第 12 节的有效性检查。

### 11.1 Inbox 领取和写入是两个不同约束

同一目标 chat 的 inbox 领取可复用 PG 短租约或等价小机制，只决定谁尝试投递；**全部聊天保存还必须受第 6 节 F2 版本保护**。电脑旧普通保存应由服务端拒绝，不能靠通知电脑刷新来保证。

ST 消息自有 metadata 保存稳定 `inbox_event_id`。通过受保护的真实宿主路径保存后，桥接读回核对 event_id、chat identity、message identity 和持久 revision，再 ACK。记录 ACK 时的保存来源，不能只记一个布尔值。

保存成功但 ACK 前崩溃时，重试先读取已保存聊天；找到该 event_id 则关联现有消息并确认，不重新生成或追加。当前读取基线版本已失效时，投递重新加载并核对事件是否已存在，再决定重试；不把旧快照绑定新 revision。租约失效的交付者停止尝试；所有实际保存仍由服务端核验 F2。

### 11.2 曾交付、当前存在、已读与通知状态分开

`delivered` 表示该事件曾成功写入指定聊天。另记录当前消息链接状态，例如 present / removed / invalidated，供用户有意删消息、删 chat 或回档后更新；链接失效不撤销历史交付事实，也不触发自动补投。

因此：ACK 后被旧快照覆盖属于应被 F 阻止的并发风险；用户后来主动删除属于有效操作，应对账并撤销相应派生来源，不能把它当丢消息修复。应用内已读、系统通知提交/到达是另外的状态，按照已确认 D2 邮箱＋飞书范围实施，不互相冒充。

首版覆盖用户指定的 Anthropic Messages、Chat Completions、Responses 三种协议，模型配置和费用见第 17 节。严格剧情对首版声明支持的协议 / provider / 扩展组合检查最终请求；未适配的能力明确拒绝，不静默降级为信息边界更弱的路径。

## 12. 来源标识、漏报恢复与检索前对账

本节是针对“ST 已保存编辑/删除，浏览器尚未通知 Go 就关闭”的设计补齐，未运行复现或验证。最小机制为**保存事件加速＋服务端持久来源对账兜底**；不建立大型事件溯源平台。

### 12.1 稳定来源与读取状态

来源至少包含 ST 用户、稳定 chat identity、角色实例、branch、稳定消息标识、当前 swipe 和内容修订/hash。数组下标和文件名只用于定位，不作持久身份。自有 metadata 中的 ID 须验证原生导出、分支和目标插件能保留；重命名保持 identity，新分支另建 identity。

Go 记录每个来源的已应用 revision 和有效状态。事实、摘要、画像、向量、跟进事项及后台任务记录相应来源依赖。只记摘要文字而不记依赖，无法可靠撤销编辑/删除的影响。

ST 桥接读取明确区分：成功取得持久快照、已确认删除、同 identity 改名、暂时不可读/格式异常。原生空数组、超时或解析失败不能直接当作删除。对确认删除才执行删除来源的失效规则；读取失败保持待核对，不永久误删。

### 12.2 三类恢复触发

1. **打开聊天或恢复连接**：核对该 chat 当前持久修订；先对账失效旧来源，再刷新本项目记忆面板及允许相关注入。不能只信任浏览器内存或之前的 ACK。
2. **准备检索/模型上下文**：先取得候选来源，再按 chat 去重批量核对本次拟注入事实、摘要、画像的依赖 revisions。必须覆盖来自其他 chat 的候选，原聊天没有重新打开也不能继续使用已删除来源。发现变化时先失效旧结果，必要时重新召回一次。
3. **后台主动生成和提取提交**：使用同一服务端核对路径；来源变更、删除、branch 失效后，旧任务的结果不能提交，也不能根据已删除计划继续问候。

前台消息事件先成为 pending observation。文本已经保存与复杂卡变量已经结算分别核验；不以固定 sleep 推断完成。事件通知可使更新更快，但浏览器通知漏报不能成为永久漏同步。

### 12.3 差异应用与派生项处理

核对持久消息清单，识别编辑、删除、所选 swipe 和 branch 变化。在 Go 一次事务中使旧来源及依赖它的事实、摘要/画像和跟进项失效或标为待重建，更新已应用 revision，并取消旧任务。随后异步提取有效新来源。后台提交再次检查 source revision 和删除代次，防止迟到结果复活。

旧摘要/画像不能在对账后继续作为缓存静默注入。依赖不完整的汇总先标待重建，或由已经核对的有效事实重建。外部引擎若异步删除向量/图/画像，结果仍必须经过本项目有效来源过滤；不能提供可核验来源及撤销能力的候选不满足正式接入要求。

模型上下文只纳入本次核对快照中有效的来源；最终组装前若检测到这些 revisions 已改变，应重核对或剔除受影响内容。已经发送到模型的旧请求不能追溯撤回。长期记忆资格撤销与 ST 当前聊天原文是否仍进入上下文是不同问题，按数据权利说明处理。

### 12.4 暂时无法核对时的降级

暂时不可读的来源不得继续放入专用长期记忆注入块。普通聊天可清楚显示本轮部分长期记忆不可用，使用其余已核对信息；严格剧情保持知情边界，必要时暂停相关动作。不能把降级替换成“继续注入旧摘要”，也不能把网络错误转换为永久删除。

### 12.5 控制开销和恢复范围

只核对当前 chat 及本轮候选/汇总依赖集合，先批量比较持久 revisions，仅对变化的 chat 读取消息清单做差异；相同版本复用已应用索引。不每轮全盘扫描所有用户、所有聊天原文。受控写入更新版本和缓存；重启、恢复备份或发现外部变更后，先对注册绑定做范围内重核对，未验证缓存不得作为权威。

记忆服务失败不应丢失已保存聊天。测试必须包含保存后通知前崩溃、从另一 chat 召回、旧任务迟到，以及读取暂不可用的恢复。调试仅传用途所需文本、来源和状态摘要，使用合成/脱敏数据，不捕获整个浏览器对象或记录密钥。

## 13. E3：不迁移旧聊天，保留旧数据责任

用户明确“不需要迁移旧聊天”，本包新增 E3。首版不把旧 conversation / message 导入 ST，不做续聊迁移，不要求旧 Vue 只读历史入口；A1 下允许退役旧前端。旧数据保留与界面代码是否保留是两件事。

先只读盘点旧数据域、账号 / relationship 标识、加密和导出删除机制，记录实际位置与负责人。旧原文保留在原库或受保护的离线归档，禁止初始化、重构清理或容器升级顺带清库。将应用回退和数据恢复分别说明；没有用户的明确删除指令不删除旧数据卷。

旧角色静态人设若能直接复用，可通过已有卡导入路径重建 V2 实例；账号身份关联按认证和数据权利需要保留。旧关系经历、来源快照、记忆和摘要不因“同一名字”自动挂到新实例。来自旧聊天的记忆若不能继续验证来源和执行纠正 / 删除，则保持归档或非检索状态，不进入 V2 模型上下文。需要保留某项已有能力，不等于需要把旧聊天内容迁移进新产品。

旧数据的导出 / 删除职责仍完整保留：可复用现有导出机制，或提供一条明确可执行的受保护管理操作，不必维持整套旧前端 / 旧生成服务。在线旧数据仍在跨域编排范围；离线归档在清单中标明位置、恢复 / 导出 / 清理办法及保留期限，不把“没有迁移”写成“已经删除”。后续若用户要求续聊迁移，再作为独立范围处理。

本轮只修订材料，不读取生产聊天、不解密生产记录、不进行归档或删除操作。

## 14. 保留现有密码与 TOTP，只有一个可见登录入口

旧 PRODUCT 的密码＋TOTP 能力要求与已确认路线不冲突，继续保留；用户允许重构具体实现。P1 可在仅合成数据的本机 / 隔离网络使用 ST 自身密码账号跑通复杂卡；P2 完成时必须接上原有认证边界。

优先复用现有反向代理和 Go session / TOTP 完成态检查。新增或接入一个只读认证校验适配接口，返回是否允许访问和服务端映射的 ST handle；这是待实施接口，不假定旧仓库已有某个具体 URL。代理对全部受保护 ST 页面、原生 API、扩展和用户资源执行校验；未认证、TOTP 未完成、会话失效或校验故障均不放行。已有 Nginx 可按其构建能力使用 `auth_request`，不新建身份平台。

固定 ST 版本的 `sso.autheliaAuth` 实际使用可信 `Remote-User` 头匹配已有、启用的 ST 账号；这里利用的是头适配入口，不要求安装 Authelia。配置 `enableUserAccounts: true`，`sso.trustedProxies` 仅列真实代理的 socket 来源；代理剥离客户端身份头，再注入 Go 验证结果，ST 端口只允许内部访问。不能把请求自带 owner_id、Remote-User 或 X-Authentik-Username 作为可信身份。

可信头主要用于自动登录；已有 ST 会话不会因为头改变就自动切换。Go 注销或切换账号时同步清理 / 重建 ST 会话。在 ST 用户解析后、原生资源及业务路由前校验当前 ST handle 与可信映射一致；若公开扩展无法覆盖此范围，允许一个有说明的最小绑定补丁。首版实际只映射本人一个账号；多账号切换检查使用合成账号。

必要验收只覆盖这条实际边界：未完成 TOTP 被拒；完成后一次可见登录进入正确 ST 用户；伪造身份头无效；持有旧 ST cookie 也不能绕过已注销 / 过期的 Go 会话；账号切换不读到旧账号数据；校验故障不放行；原生卡、模型请求、扩展和 CSRF 仍正常。不要将保留旧 Go TOTP 源码误报为新入口已完成认证集成。

依据：[ST SSO](https://docs.sillytavern.app/administration/sso/)、[ST 固定版本 users.js](https://github.com/SillyTavern/SillyTavern/blob/7e8663cd9c184a550b37238218bdd32c6efc68e9/src/users.js)、[实际 socket 来源解析](https://github.com/SillyTavern/SillyTavern/blob/7e8663cd9c184a550b37238218bdd32c6efc68e9/src/express-common.js)、[Nginx auth_request](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html)。

## 15. 存储保护变化：已选择 C1

### 15.1 已核验的现状

#### Go 的字段加密路径确实存在

- `backend/internal/store/postgres/fieldcipher.go` 实现 AES-256-GCM 的 `enc2:<keyId>:<version>:...` 信封，包含新随机 IV 和认证标签；可读旧版本用于迁移，写入当前版本。
- `generation.go` 的消息写入、`memory.go` 的记忆 summary / 提取重放 payload 等实际调用 `encryptStored`，读取时解密。
- `config.go` 在 full 数据库模式要求 `VC_CRYPTO_REST_KEY`；`app.go` 拒绝 full 模式缺 Cipher。不是只有一个未使用的加密工具类。
- 这些是固定源码的保护契约；未检查用户实际部署的密钥、历史回填和数据库内容，因此不声称每个旧数据副本已全部加密。

来源：[FieldCipher](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/store/postgres/fieldcipher.go)、[消息写入](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/store/postgres/generation.go)、[记忆写入](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/store/postgres/memory.go)、[配置约束](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/config/config.go)、[运行时约束](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/app/app.go)。

#### ST 的原生落盘边界不同

- 官方多用户文档明确聊天、API Key 和其他敏感数据以明文存于服务器文件系统。
- 固定 `chats.js` 的 `trySaveChat` 将消息数组逐项 `JSON.stringify` 后形成 JSONL 并保存，随后调用聊天备份函数。备份默认启用，不能只盘点主聊天目录。
- 固定 `secrets.js` 的 SecretManager 将 key 的 `value` 直接写入用户目录 `secrets.json`。`allowKeysExposure` 是取值 / 展示接口的限制，不是文件加密。旧 secrets 格式迁移还会把原文件复制到 backups。
- 原生删除单聊天接口只定位并删除对应聊天文件；不应据此假定所有自动备份、Go 来源或外部索引均被清除。

来源：[ST 官方多用户存储说明](https://docs.sillytavern.app/administration/multi-user/)、[ST chats.js](https://github.com/SillyTavern/SillyTavern/blob/7e8663cd9c184a550b37238218bdd32c6efc68e9/src/endpoints/chats.js)、[ST secrets.js](https://github.com/SillyTavern/SillyTavern/blob/7e8663cd9c184a550b37238218bdd32c6efc68e9/src/endpoints/secrets.js)。

这是已向用户说明并由用户选择 C1 接受的**保护范围变化**。该选择来自明确回复，不是以自用为理由默认降低保护，也不是已发现线上泄露。

### 15.2 C1 的准确保护范围

| 对象 / 边界 | 首版落实方式与限制 |
|---|---|
| ST 新聊天、私有状态、原生 API Key | 原生文件可保持明文；实际磁盘 / 卷保护、目录权限和加密备份覆盖主文件及自动 / secrets 迁移备份。关闭 key exposure 不是加密 |
| Go 消息、记忆、来源快照、inbox、摘要和含私密文本的任务 payload | 保留已有应用字段保护能力；新敏感文本走核验后的保护路径。允许重构实现，不能因换模块留下明文副本 |
| 外部记忆引擎 | 先盘点文本、向量、图关系和缓存的实际落盘。Go 的保护不能自动延伸到外部引擎；沿 C1 范围落实卷 / 权限 / 加密备份，明确剩余可见性，向量化不是加密 |
| 离线磁盘、备份泄露 | 未解锁加密卷和未获得备份密钥的读取者不能直接读对应受保护内容；需验证实际加密与恢复，不能只检查配置名称 |
| 运行中访问 | 有相应主机 / 文件权限的进程、应用和可信插件仍可读 ST 明文；磁盘加密不防这类读取。不是端到端加密 |
| 导出和临时文件 | 业务生成的导出可能包含明文；限制下载、有效期和暂存访问，备份纳入同样保护；不把密钥放进普通聊天副本 |

C2 全面应用层加密 ST 的路线已不选，本版不为它预留加密抽象或另做实现。若未来改变保护要求，再依据实际数据路径评估改造。C1 不取消 Go 原有字段保护要求。

### 15.3 部署时需要补齐的最小配置

1. 盘点 ST 主文件 / 自动备份 / secrets 备份、Go PG / 导出、所选记忆引擎、临时对象和含内容的日志；逐域说明保护方式。
2. 明确磁盘 / 卷和备份加密实际部署方式、受限文件权限、密钥保管及恢复办法。密钥与数据备份分开保管；把 `.env` 和数据一起打包不提供独立保护。
3. 备份保留天数和恢复条件优先继承真实已确认的策略；没有值则标运行配置待填，不编造用户已选择的天数，也不阻塞本包交付。
4. 通过正常应用路径产生合成内容，再验证落盘 / 备份和恢复。实际措施未就绪时不导入正式密钥及私人数据。
5. 不承诺未实现的按用户密钥销毁。共享服务密钥不能为删除某一角色而直接销毁，也不能把删文件或磁盘加密等同密码学擦除。

这些是 C1 的实施和运行配置，不再要求用户重新选择存储路线。

## 16. 跨存储导出 / 删除责任矩阵

Go 作为导出 / 删除编排者，优先复用已有 data export 和 durable deletion intent；质量不足时允许重构，仍须保留可靠续作和正确完成语义。ST 插件处理其文件与关联备份，外部记忆适配器执行命名空间操作，不新建隐私平台。

| 数据 | 导出责任与范围 | 删除责任与完成证据 |
|---|---|---|
| E3 保留的旧 Go 聊天、消息、关系 / 记忆 | 保留可执行的旧数据导出 / 归档访问办法，列明位置和密钥需求；不因不做历史 UI 而遗漏；本版没有 ST 迁移副本 | 在线旧数据由 Go 清理，离线归档按清单执行并报告状态；未授权删除时保留；不用“未迁移”冒充“已删除” |
| ST 新聊天、swipe、分支、当前 metadata | ST 插件读取用户范围的原生数据并提供逻辑导出；与旧记录记录来源、版本和去重关系 | ST 侧删除目标原文与纳入在线范围的副本 / 索引；Go 失效对应来源及派生项；其他分支副本按明确选择处理 |
| 用户卡、私有世界书、偏好和实例绑定 | 包含用户内容与必要引用；共享上游资产按许可及归属处理 | 删除该用户私有副本与绑定；不删其他用户或全局共享依赖 |
| 记忆、摘要、画像、来源快照 | Go 汇集实际仍保留的数据、scope、来源和修订；外部引擎已产生的摘要 / 画像等纳入 | Go / 引擎同时执行；移除可检索内容、派生摘要和索引；旧任务提交前检查 tombstone / revision |
| inbox、跟进、邮箱 / 飞书通知记录 | Go 导出内容、计划时间、目标的适当表示、状态和 ST 消息映射；凭据排除 | 取消未发通知及后续重试，清理持有用户文本的任务；已发送到收件箱 / 飞书的外部副本不承诺能由本应用撤回，按渠道能力准确说明 |
| 后台任务和模型结果 | 导出涉及用户的语义输入 / 结果及必要状态；不导出服务凭据、内部租约令牌 | 先停止新任务和结果提交，再取消待执行任务，删除持有用户文本的 payload / 缓存；保留不含原文的最小完成记录 |
| 外部记忆引擎的向量 / 图 / 画像 / 缓存 | 适配器导出该 owner / instance 范围的记录及派生关系；可再生成的索引若不带出，要在清单明确，并提供其对应语义数据 | 对相同 namespace 全面清除；只删 Go 中记录 ID 不算完成。引擎不可用时保持 pending / failed，不报全部删除成功 |
| 已生成导出文件与临时文件 | 新导出不把旧导出重复套入；记录生成范围和有效期 | 撤销下载权限，清理对象存储与本地临时文件；沿用既有一次性下载和删除屏障 |
| API Key / 会话 / TOTP 等凭据 | 普通“聊天与记忆副本”默认排除密钥值；只导出非秘密配置引用和存在状态 | 删号撤销对应会话和该账号私有凭据；服务全局共享配置不因单个用户删除而清除；用户需在上游撤销的 API Key 明确告知 |
| 自动备份、快照、离线备份 | 不把历史已删除内容重新拼入用户在线数据导出；报告保留政策 | 可定位的应用在线备份按删除范围清理；不可变 / 离线备份按公开保留期到期，单列预计清理时间，不声称立即清除 |

外部引擎若无法隔离并导出 / 删除用户范围的派生数据，不满足首版真实私人数据接入条件。用合成样例评估；不能因删除适配尚未完成就让真实记忆进入后声明成功。对真正的远端模型服务留存，产品只能说明已发送范围及供应商能力，不能承诺从对方日志中自行抹除。

### 导出的最小完成条件

复用现有导出任务建立一份跨存储清单：数据域、来源系统、用户 / 实例范围、实际记录数、源版本 / 截止时间、文件名、缺项和状态。执行时可短暂暂停该用户受控写入，取得 ST 保存版本与 Go 相关状态的一致采样；如果只能取得不同时间点，必须逐域标注，不能称为跨系统瞬时快照。

只有全部承诺数据域可读且清单核对通过，才称“完整副本已生成”。外部引擎不可达时允许明确提供“部分副本”，列出缺项；不得返回一个缺数据的文件却继续称完整。导出文件本身是敏感内容，沿用现有一次性下载、有效期、访问控制和对象清理；存储保护按已选 C1 覆盖。

### 删号的最小可靠流程

1. 复用 Go durable deletion intent，先登记删除范围及 ST / 外部 engine 标识。冻结该用户新前台生成、ST 保存、后台生成 / 提取 / 投递和结果提交；已发给供应商的请求尽力取消但不能假装收回已发送数据。
2. 用现有持久任务扩展少量分项状态：Go（含仍在线的旧数据）、ST、外部记忆、通知任务、导出对象及归档清单。操作幂等，进程重启可继续；所需映射在删除主账号前保存到最小清理记录中，避免账号先 cascade 掉导致外部数据找不到。
3. 每侧确认清理完成，旧任务不得重建。ST / 外部引擎离线则保持“删除处理中，未完成项：…”，不标所有在线数据删除成功。业务访问继续阻断。
4. 所有在线数据域确认后报告“在线数据已删除”；另列备份保留截止日期和清理状态。最小删除标记不存聊天原文，用于防恢复复活。
5. 删除标记需要保留到可能包含旧数据的备份全部过期。恢复备份时先在隔离状态加载最新删除标记并执行清理，再允许检索、生成和后台任务。不能仅恢复一份删除前的数据库然后立刻开放使用。

既有机制来源：[导出任务](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/jobs/export.go)、[删号 HTTP 流程](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/httpapi/account.go)、[持久删除意图](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/migrate/sql/V103__durable_account_deletion_intent.sql)、[删除期间清理导出对象](https://github.com/hxf4869/virtual-companion/blob/baa26f7bd2cf50f23058b030e1bc690a5fb553d4/backend/internal/migrate/sql/V137__export_cleanup_during_deletion.sql)。

### 16.4 四种不同产品语义必须分开

| 用户动作 | 实际承诺 | 不能暗示的效果 |
|---|---|---|
| 删除长期记忆 | 对选定记忆及其派生摘要 / 画像撤销，阻止同一来源修订被旧任务重新提取；来源抑制信息按策略保留 | 不等于删除 ST 原文；当前聊天历史仍可能把原话发给模型 |
| 删除聊天原文 | 删除选定聊天 / 消息及定义范围内副本，失效 Go 来源与依赖派生项；分支、备份范围清楚列明 | 不等于其他独立来源包含的同一事实自动全部清除；不等于离线备份立即抹除 |
| 不再用于后续模型上下文 | 从本项目受控后续请求的历史、检索、摘要、工具结果、来源缓存中排除选定来源，检查最终发出的请求 | 不能收回已发送请求，不能让模型“忘掉”供应商已有数据；未适配的额外生成插件不能自动获得该承诺 |
| 清理备份 | 删除可清理副本，或按明确保留期到期；恢复时应用最新删除标记 | 不能因主文件删除就说备份也删除，不能将磁盘加密说成删除 |

建议实际按钮保持清晰：“删除这条长期记忆”配说明“聊天原文仍保留，可能继续用于当前对话”；“删除聊天及其派生记忆”展示范围；如首版实现排除上下文功能，标为“后续回复不再使用这些记录”。没有完成最后一类控制时，不以“已彻底忘记”之类文案替代。


首版不必为了区分语义而另造通用内容审查平台。若没有完成“后续上下文排除”控制，只提供真实的记忆/原文删除功能及准确说明；不得显示彻底忘记。若提供排除功能，其受控历史、检索、摘要、工具及目标插件额外请求都需通过最终请求验收，不能只在Go记忆层过滤。

## 17. G2 模型配置、三协议与费用边界

### 17.1 统一入口、单一登记和真实生效配置

用户已选择 G2，按用途独立绑定配置，不要求现在写死供应商或模型 ID。统一入口位于 ST 扩展页面，遵循 [DESIGN.md](../DESIGN.md) 和用户截图。Go 保存本产品模型登记、用途绑定、配置 revision 与预算；ST 继续执行原生前台生成。它们是同一逻辑配置的登记与运行投影，不能各自长期独立修改“同一用途”的两份值。

工程上复用已有 profile / 配置结构，用最小字段表达以下三层；不为名称拆分而新造配置平台：

| 层次 | 必需内容 | 规则 |
|---|---|---|
| 供应商 | ID、显示名、启停、协议、Base URL、凭据引用 | 支持多个自定义供应商；协议使用下面三个明确枚举，URL 不因名称猜测；凭据只保留一个权威副本 |
| 模型配置 | 模型 ID、所属供应商、上下文窗口、最大输出 Token、输入类型、输出 / 工具 / 推理能力、请求参数；可选输入 / 输出计价元数据 | 模型 ID 可手填，拉取模型列表是辅助；不能要求第三方代理一定实现列表接口；模型能力不是由一个 ID 自动保证 |
| 用途绑定 | 前台 / 提取摘要 / 后台问候 / 剧情导演 / NPC 的 model profile 引用、启停、限额、配置版本 | 每个用途固定引用自己的配置；可选同一配置，不强制必须用不同模型；未配置标待配置，不自动回退 |

G2 的“固定”表示绑定引用稳定，不是永久冻结该 profile 的一切字段。编辑共享 profile 的 provider、URL、模型或限额会影响所有引用它的用途；保存页面展示受影响用途，提供另存为新配置的普通操作。只切换某角色前台绑定，则不改变其后台和剧情绑定。

普通页面、卡文件、日志和数据副本不携带密钥值。密钥可复用既有 Go 保护存储或 ST SecretManager，但每个供应商 / profile 必须选定唯一凭据权威和内部取用方式，不能两侧各留一份可独立修改的长期密钥。ST 原生凭据采用 C1 边界；后台按受控服务端接口读取所需值，浏览器不获得内部服务凭据。凭据撤销立即影响后续请求。

### 17.2 三种协议是首版要求

| 协议 | 基础 URL 与请求路径 | 实现 / 验证要求 |
|---|---|---|
| `anthropic_messages` | Anthropic Messages，典型最终路径 `/v1/messages` | 复用 ST Claude 路径和成熟客户端；按实际 provider 处理鉴权 headers、system、content blocks、工具和流事件 |
| `openai_chat_completions` | Chat Completions，典型最终路径 `/v1/chat/completions` | 复用 ST Custom / 原生路径；核验 tools、结构化输出、流式 usage 与取消行为 |
| `openai_responses` | Responses，典型最终路径 `/v1/responses` | 先查询成熟适配，补齐 ST 所需请求 / 流式桥接；不能只把 Chat Completions 的路径替换成 responses |

Base URL 允许自定义，保存界面显示规范化后的**最终请求地址**，按协议清楚说明是否已含 `/v1`。避免 `/v1/v1/messages`、重复 endpoint 或把带完整接口路径的输入悄悄拼错；对有意采用其他兼容路径的服务，按明确 URL 配置验证，不暗中改到另一供应商。连接测试是显式操作，标明可能调用真实模型和产生费用。

固定 ST 1.19.0 的静态源码中，Claude 路径可见 `/messages`，Custom 路径可见 `/chat/completions`；未找到 Responses 请求实现。因此 Responses 是确定的工程验证 / 适配任务，不可写为三种已原生可用。具体方案优先复用成熟库和本仓库可用实现，必要时以小型服务端适配完成；不为这三种协议另建通用模型网关。

三协议分别验证文本输入、流式 / 非流式、结束原因、错误、取消、usage、工具调用与结构化输出的实际支持范围。Responses 的 input / output items、事件流、工具循环和必要的延续状态须正确映射；Anthropic 的 system / block / tool 语义不能被当作换字段名处理。原始不可支持能力返回明确错误或显示不支持，不静默丢字段，不用另一协议或模型伪装成功。

复杂卡、剧情、记忆的验收必须观察最终请求和真实持久结果。先用本地固定 provider 做协议形状 / 流事件确定性测试；真实 provider 结果需另行在已配置与预算范围验证。首版三个协议都应可实际配置和调用，不能只验证 Chat Completions 后把另两个下拉选项算完成。

来源：[ST 固定后端实现](https://github.com/SillyTavern/SillyTavern/blob/7e8663cd9c184a550b37238218bdd32c6efc68e9/src/endpoints/backends/chat-completions.js)、[ST 固定前端配置](https://github.com/SillyTavern/SillyTavern/blob/7e8663cd9c184a550b37238218bdd32c6efc68e9/public/scripts/openai.js)、[Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create)、[OpenAI Responses](https://developers.openai.com/api/reference/typescript/resources/responses/methods/create)。这些为接口 / 源码依据，不是运行结果。

首版严格剧情采用显式上下文：每个新回合从当前 ActorView 组装实际输入，不以 Responses 的 conversation / previous_response_id 等远端历史引用跨回合续接，也不复用其他角色或旧分支的不透明上下文。官方 [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state) 说明这些引用能够继承先前内容，因此只检查当前可见 payload 不足以证明隔离。

同一受控工具回合如需回传本次模型输出 / reasoning 项，限定在相同 owner、instance、run、branch、actor、config revision 与来源版本；上下文变化、取消、回档或来源移除时丢弃旧回合续接状态并重新构造。首版不建设跨回合远端会话管理器。store:false 可按供应商语义减少保存，但不能单独证明没有继承历史，也不等于删除供应商全部日志。

### 17.4 用途绑定和切换规则

| 用途 | 执行方与绑定 | 未填写时 |
|---|---|---|
| 前台聊天 | ST 原生生成链；角色 / 会话指向其明确配置 | 配置待填，不能偷偷使用全局旧 Key |
| 记忆提取、去重、摘要 | 一个后台提取路径，独立绑定 | 后台真实调用不启用；固定 provider 验证可继续 |
| 主动问候 / 跟进 | Go 后台 profile，绑定人设版本、频率与预算 | 计划可配置，但无真实生成与试发 |
| 剧情导演 / NPC | Go 规则决定可见信息，ST / 已选执行链仅执行一个明确请求；导演和 NPC 可各自绑定配置 | 严格剧情先用固定 provider 验证，真实叙事待配置 |
| Embedding | 需要向量召回时独立选择模型、接口、维度和预处理版本 | 默认未启用，使用已验证关键词基线；不能把三种聊天协议自动当 embedding 协议 |

各用途首版只有 `pinned` 与 `pending/disabled` 等必要状态，不因为 R2 曾推荐 G1 而强制再实现 follow_chat。多个用途允许固定到同一 profile，但是否共享是可见绑定。

ST 原生设置仍可能被直接编辑。生成前核对实际 provider / endpoint / model / 参数指纹；原生变更更新前台绑定的版本或生成一个新的明确 profile。需要修改共享配置时显示影响用途，不静默改变其他用途；无法可靠同步则暂停**受该共享变更影响**的任务并提示。独立固定后台不因前台换模型被误判为漂移，也不因无关前台配置变动被无端阻塞。密钥值不进入公开指纹。

排队任务保存用途与逻辑 profile，实际开始时解析并记录不可变快照；正在运行的单次 run 不因配置修改中途换模型。记录 config_revision、实际 model / endpoint 标识、用途、请求次数和 usage；重试按原策略和额度处理。修改 provider / endpoint / model 后再次核对该用途的允许范围及预算，超出运行授权时标 pending_authorization；G2 和配置保存本身不扩展真实费用或数据发送授权。

Embedding 版本 / 维度 / 预处理变化时重建匹配索引或显式切换，不混查不同空间向量。无需支持无限组合，也不必为尚未采用的外部引擎写适配骨架。

### 17.5 费用与运行配置

用户确认的是 G2 配置能力，未给出具体提供商、模型、真实验收金额及后台日预算。相关值保持 `PENDING_CONFIGURATION`，`real_model_calls_authorized=false`。它们是运行前配置，不阻塞本包生成和后续获授权的无外部费用开发；已有 API Key 或过去用过账户不自动授权本次新用途。

运行前通过统一设置填写：选用配置及允许用途、一次真实验收总上限与币种、长期后台日上限 / 暂不开启、必要的请求 / token 限额和有效期。价格与供应商配额由执行者在用户给定范围内核验，不再让用户决定 MemoryCore / Pi 或具体扩展版本。

至少分开三类：

1. **确定性集成**：固定 provider / mock，独立标记，不产生外部模型费用；不把它算成真实模型质量通过。
2. **真实模型验收**：一次批次的总金额 / 币种、允许用途、配置、请求 / token 限额和有效期；不自动转成无限期授权。
3. **长期后台运行**：日总池或用途限额，覆盖问候、提取、摘要、去重、重试和 embedding；尚未开启则无真实后台调用。

预算覆盖同一工作流全部外部调用：主回复、工具后续、MVU 可选额外请求、剧情导演与 NPC、摘要、提取、去重、重试和 embedding。目标扩展额外调用若不能纳入计量范围，先关闭该额外调用路径并准确标识兼容范围；主回复费用不能冒充全卡费用。通知服务若收费，其账户配额 / 费用单独配置，不从模型预算自动授权。

最小执行机制可复用 PG 任务状态：发送前原子预留本次保守上限，结束按 usage 结算，并发任务共享余额。达到限额、授权缺失或无法算出已授权上限时停止新请求；超时不把费用当零，未核对预留保留，重试另计。取消能停止后续调用，已发出的请求可能已经计费。

提供商价格未知、usage 缺失、动态计价或在途请求存在时，不宣称应用层精确保证实际账单金额。请求 / token 限额与应用估算要分开显示；强金额上限需供应商真正支持的账户 / 项目限额并核验语义。真实付费验收缺可靠条件则保持 BLOCKED，不能自行猜价放行；本地免费 / 固定 provider 不因此被阻塞。

### 17.6 对应验收重点

- 前台从 A 切换 B，独立固定后台仍为其所选 A，界面与实际请求一致；修改共享 profile 则显示影响用途，任务使用新 revision。
- 从原生 ST 直接修改配置能被核对；只暂停实际受影响的用途，旧凭据撤销阻止后续请求。
- 三协议的最终 URL、请求、流式、取消、错误、usage 和必要工具 / 结构化输出分别验证；不能只测 UI 选项。
- 截图能力字段区分声明与验证，未知或不支持能力有准确提示；输入 / 输出 token 和价格单位明确。
- 未配置用途或预算时没有真实调用；并发预留、超时和重试不重复释放预算；embedding 不混用不同空间。

### 17.6 剧情世界提交与聊天投影的恢复

世界事件与 ST 聊天不做跨系统分布式事务。Go 世界提交与“待投影”记录放在同一已有 PG 事务 / 持久任务机制中；world_event_id 是稳定投影键。世界动作成功但 ST 保存冲突、请求丢失或浏览器关闭时，只重载最新 chat revision 并幂等补写已确定结果，不重新执行规则动作或生成一个新的物品转移。

界面显示“行动已生效，聊天记录待同步”，分别报告两侧状态。读回发现投影已存在则确认，不重复追加；世界已回档 / 分支失效或用户主动删除已存在投影时不自动补回。删除聊天投影不会偷偷撤销权威世界动作，世界变化由明确回档 / 动作规则处理。验收归入现有 S02 与剧情样例，不新增协作或事务平台。
