# Virtual Companion V2 总方案 · R3

日期：2026-10-27（Asia/Shanghai）。当前交付为完整需求与执行材料，应用尚未实施。原静态证据固定在明确版本，未来执行先核对最新仓库，不能把设计缺口写成已经运行复现的故障。

## 1. 产品目标与确定范围

产品包含三个相连的体验：

1. **长期陪伴**：多个可编辑人设的角色，各有独立关系、记忆和共同经历，能持续聊天、问候、跟进用户事项，并使用少量明确工具。
2. **原生酒馆**：角色卡、世界书、预设、正则、脚本、变量、状态栏和目标扩展真实运行，尽量直接复用生态。
3. **受规则剧情**：用户与三个 NPC 进入案件，每个角色只知道自己有权知道的线索，行动受规则裁决，支持阶段、证据、回档和结局。

**已确认首版是完整 P0–P6，包含 P5；通知渠道为邮箱与飞书；旧聊天不迁移。** 浏览器是主客户端，ST 是主入口；调整原 Vue / uni-app 规划，首版不交付微信小程序。个人非商业用途保持。

权威选择见 [DECISIONS.md](DECISIONS.md)；[decisions.json](references/decisions.json) 是同一选择的结构化表达。当前没有未决产品分支，模型 / 预算 / 收件人等是运行前配置。

## 2. 架构与重构原则

**原生 SillyTavern Node 宿主 + UI extension / server plugin + Go 长期服务 + PostgreSQL。**

ST 承担真实复杂卡运行、原始聊天和前台生成。Go 承担关系与角色实例、记忆生命周期、后台任务、主动消息、通知、模型用途配置与预算、严格剧情权威状态。PostgreSQL 保存长期结构化数据与必要持久任务。外部记忆引擎和 Pi 只有满足具体缺口时才加入。

用户已经授权彻底重构旧模块。实施时逐个判断 **直接复用 / 改造 / 替换 / 删除**，保留的是产品需要的行为、数据保护和运行能力。不要为了保住旧接口、旧分层或不再使用的 Vue 页面长期叠两套实现。也不要因允许重构而清空所有成熟能力，或把 ST 逐行翻译成 Go / Rust。

处理顺序为：查现有代码与依赖 → 查官方资料和 GitHub 实现 → 确认适用性、许可与具体缺口 → 用最小案例验证 → 开发必要差异。一个模块研究足够后就推进；不用维护多套同类框架或通用适配平台。

代码重构不授权删除旧业务数据、覆盖未提交修改、修改远端生产服务。旧数据先隔离保管，代码可以按 V2 明确边界退役。

## 3. 设计先行，前端仍使用真实 ST

设计流程明确为：

**DESIGN.md → Stitch 桌面 / 手机页面 → ST 主题、布局、组件和扩展页面实现。**

[DESIGN.md](DESIGN.md) 提供视觉基线、交互规则、页面清单、状态、手机适配和逐页提示词。优先完成聊天、角色 / 记忆、模型设置、通知、剧情页面及冲突态。面向用户的页面实现依赖对应设计稿；兼容实验、来源机制和后端工程可并行。

原生宿主行为是兼容前提。主题和扩展不能改掉第三方脚本依赖的生命周期；不因为 Stitch 导出 React 页面就另建独立聊天宿主。复杂卡内部 iframe / 样式保持边界，宿主只规范外壳。手机上的角色切换、键盘输入、长表单、状态栏、swipe、世界书和保存冲突在 P1 提前验证。

色彩、字体和尺寸是工程设计基线，尚无实际 Stitch 产物；包内截图仅作为用户要求的模型配置字段参考。工具能力不足时准确标未生成，不用占位图或其他工具结果冒称 Stitch 图。

## 4. 数据与配置的权威归属

| 数据或行为 | 权威归属 |
|---|---|
| 卡、世界书、预设、原始 ST 聊天、swipe / 分支 | ST；Go 通过受控接口读来源和派生信息，不并行修改 JSONL。 |
| 自由复杂卡变量 | 原卡 / MVU；Go 不共同改写同一变量。 |
| 角色实例、关系、长期记忆、跟进、inbox | Go / PostgreSQL；来源与 ST 当前持久状态一致。 |
| 严格剧情真相、行动、证据权限、结局条件 | Go 世界状态；每个 NPC 的可见投影进入对应模型请求。 |
| 普通前台生成 | 原生 ST 执行链；Go 不为同轮输入重复生成回复。 |
| 模型定义、用途绑定、配置版本和预算 | 一个逻辑目录，由 Go 管理；ST 前台配置是受版本同步的运行投影。 |
| 邮件 / 飞书投递 | Go 持久任务；一次通知事件按渠道分别记录结果。 |
| 旧 Go 数据 | 旧存储保管与可控导出 / 删除；不迁入 ST，不自动进入 V2 召回。 |
| 导出与删除编排 | Go 协调；ST、旧存储及实际选用的外部引擎各自负责数据域并报告完成情况。 |

模型目录只维护一个权威版本，避免 ST 和 Go 各有一套隐形配置。ST 原生入口的配置修改要反映到前台绑定；独立固定的后台绑定保持不变。修改共享 profile 的 URL / Key / 模型配置时，界面明确列出受影响用途，运行中单次请求保留不可变快照。细节见 [架构](docs/03_architecture.md)。

## 5. 六项不能丢失的可靠性要求

### 5.1 C1 存储保护

用户已接受 ST 原生聊天与秘密文件的明文边界。实施磁盘 / 卷保护、最小目录权限、加密备份、密钥保管和恢复说明，保留 Go 字段加密能力。当前挂载环境中具备相应读取权限的进程仍可读取 ST 文件，不能写成与应用层字段加密等价。[ST 官方说明](https://docs.sillytavern.app/administration/multi-user/)

C2 不是首版工作，不为加密 ST 存储另建通用持久层。实际部署保护尚未验证；正式私人数据与密钥接入前落实对应配置。

### 5.2 F2 覆盖每次聊天保存

版本令牌来自加载时的真实快照。普通消息、编辑、脚本 / MVU 自动保存、swipe、删除、重命名、分支、回档、导入覆盖及群聊保存都受同一服务端边界保护。比较与提交要原子化；force 不绕过保护。

手机写入主动消息并 ACK 后，电脑携带旧快照保存必须冲突拒绝。同一浏览器晚到的自动保存也不能覆盖新状态。冲突时保留本地草稿、加载最新，再由用户处理；不自动合并复杂卡变量或剧情状态，不加入 CRDT / OT 多人协作系统。

inbox 租约、event_id 和读回 / ACK 在此基础上工作。历史交付成功与当前消息是否仍存在分开；用户合法删除或回档后不自动补投。

### 5.3 来源事件漏报后的恢复

浏览器保存事件只是加速通知，持久来源读回负责正确性。在打开聊天、重连、检索准备、后台生成和提取提交时按需对账。

检索先拿到候选及摘要 / 画像依赖，再核对各自来源聊天，包含用户没有重新打开的旧聊天；来源变化先撤销旧内容资格，再异步重建。旧提取结果按 revision / 删除代次拒绝，不能复活。

确认删除、重命名、成功读取空聊天、临时错误必须区分。读取失败时旧记忆与相关摘要暂不注入，不能误删全部数据，也不能用旧摘要作为绕过校验的降级。不做每轮全库扫描或大型事件溯源平台。

### 5.4 数据权利和 E3

“不迁移旧聊天”只取消转换和历史 UI 工作，不代表获准删除旧库。保留旧数据的存放位置、归属、导出 / 删除办法；允许用既有维护入口或最小离线工具处理旧库，不维持整套旧前台。

旧聊天对应的记忆、摘要、来源快照默认不自动接入 V2。若某个非聊天资产明确复用，必须有有效来源与范围，不能靠旧摘要偷偷恢复未迁移历史。角色卡模板与私人经历分开处理。

新数据的导出 / 删除覆盖 ST、Go、来源快照、记忆、inbox、后台任务和所选外部引擎派生数据。删除先保存持久意图和所需映射，阻止新结果复活；分项失败就保留待清理状态。普通导出不包含 Key。

产品文案区分：删除长期记忆、删除原文、排除后续受控模型上下文、备份清理。原文仍在 ST 当前历史中时，删除记忆不能承诺“模型永远看不到”。备份恢复先应用最新删除标记，再开放任务和检索。

### 5.5 时间语义

来源 timestamp / timezone、记录时间、事件日期、提醒时刻分别表示。来源中的相对日期按来源时间解析，查询的相对日期按查询时间解析；抽取延迟与重试不能改变已确定的事件日期。

M01 使用明确的 2026-10-30；M11 验证 10 月 20 日和 10 月 27 日说“下周五”的不同结果；M12 对时区缺失的相对日期保持待澄清。只有日期不捏造零点提醒。原十二个记忆案例保留。

### 5.6 三协议与费用

统一提供三协议配置：Anthropic Messages、Chat Completions、Responses。协议、Base URL、模型和能力分别配置；界面展示实际请求地址，避免重复拼接 /v1 或 endpoint。能力声明不等于已验证。

三协议的消息 / system 语义、流事件、工具循环、取消、错误、usage 与剧情最终请求都需有对应验证。固定 ST 1.19.0 的 Responses 适配是明确工程工作，不能只改 URL。原生已经可复用的路径优先复用，缺口再引入最小 SDK / 协议适配；不搭建独立通用模型网关。

真实模型与后台预算未提供，保存设置不触发调用。费用包括扩展附加请求、工具后续、提取、摘要、重试和 embedding；金额、请求 / Token 限额、估算与真实账单各自说明。三协议验收可先用固定 provider，不据此宣称真实模型效果已经通过。

## 6. 长期陪伴与有限 Agent

多个角色可以独立保持关系、个人经历和记忆；同款角色卡的不同实例不共享私人经历。召回使用当前问题、角色 / 用户 / 会话 / 分支范围和相关度，不是最近若干条聊天截断。

记忆含来源与修订，用户可查看、纠正和删除。待跟进事项有触发条件、时区、状态、重复抑制、静默时间及预算。主动行为围绕用户已说过的事项和关系状态，允许不发送，避免每个定时扫描都制造问候。

受浏览器脚本限制的复杂卡操作，离线时只产生 waiting-host 意图或普通已声明的陪伴消息；不宣称后台 Node 自动执行浏览器里的所有卡脚本。工具限当前明确需要，优先现有 ST 工具循环与成熟 Agent 部件，不直接给角色任意 Bash / 编码权限。

MemoryCore 是第一外部记忆候选；其 scope、来源、纠正、删除、导出以及性能需要实际通过。现有 Go 记忆如果能用小范围调整达成要求，也可以作为首个有效基线。Pi / Cognee 按具体缺口选，不同时堆多个系统。

## 7. 主动通知：邮箱与飞书

两个渠道都是首版要求，可按角色、事件类别与用户配置启用。工程基线是 SMTP 邮件和飞书自定义群 Webhook；优先现有合格发送能力、成熟 Go 邮件库、官方协议 / SDK。

一个逻辑事件可产生多个渠道投递记录。inbox 保持事件权威，邮件 / 飞书不取代聊天持久化。无浏览器时点击通知进入应用，再按 F2 同步和展示相应消息；正文预览和链接不携带 Key。

分别记录：事件生成、inbox 持久化、ST 保存、渠道已接受、手机观察到显示、应用已读。SMTP 或 webhook 成功不能自动把 ST 标 delivered，也不能当作用户已读。

对普通重试做幂等、退避、频控和过期处理；对“请求可能已成功但响应丢失”准确记录结果不明。供应商没有幂等契约时不承诺跨渠道 exactly-once，重试策略与可能重复对用户可解释。关闭网页后，邮件和飞书都要在实际手机上验收。

首版不做微信 / 企微 / QQ 的空适配器、不引入专用消息中间件、不为仅通知强制运行完整 AstrBot 平台。后续真有渠道需求再扩展。

## 8. 三 NPC 严格剧情是首发必做

剧情世界书拆成公共背景、各角色私密事实和主持人真相；不是把完整谜底塞进群聊历史再要求 NPC 假装不知道。Go 维护权威状态和规则，模型负责在允许信息内表达与提出动作。

NPC 行动经类型化校验、权限和世界状态裁决再生效。世界已提交而聊天保存失败时，以稳定 world_event_id 补写投影，不再次执行行动。私聊、公开发言、线索发现、转交、阶段推进与结局都有明确输入输出。最终请求在所有世界书、摘要、扩展、工具结果与协议转换后验证，防止其他 NPC 的秘密进入无权请求。

原生 ST 群聊可用于自由群像，但共享历史不能自动当严格认知隔离。严格剧情采用明确受控的模式；无法约束的任意扩展不获得严格保证。三种协议各自验证最终请求与工具可见性，不能仅通过 Chat Completions 就宣布全部完成。严格剧情每个新回合使用当前 ActorView 显式上下文，避免远端会话 / previous_response_id 继承不属于当前角色或分支的历史。

陪伴角色入局可用独立剧情分身；结束后由用户选择保存公开共同游玩摘要，案件真相和 NPC 私密状态不自动写入日常陪伴记忆。
