## 2. 工程方案，不冒充用户逐项确认

| 事项 | 本包工程基线 | 调整规则 |
|---|---|---|
| 运行架构 | 原生 ST Node 宿主 + UI 扩展 / server plugin + Go 长期服务 + PostgreSQL | 用具体问题证明所需补丁；不重造酒馆运行时或为统一语言整仓改 Rust。 |
| 飞书方式 | 自定义群机器人 Webhook，用于单向通知 | 在用户配置的目的群内接收；若实际账号需要应用私聊，工程上评估官方 SDK，不能把群送达冒充私聊。 |
| 邮件方式 | 现有合格 SMTP 实现或成熟 Go 邮件库，TLS 与服务商支持的认证 | 不自研 SMTP 协议；服务器接收、最终收件与手机显示分别验证。 |
| 通知内容 | 默认泛化标题 + 受登录保护的应用链接，预览正文可配置 | 首版不扩为在所有平台中继续完整聊天。 |
| 模型管理 | 一个逻辑配置目录，由 Go 管版本和用途绑定；ST 原生设置是受同步的前台运行投影 | 检测 ST 原生入口的变更；独立固定的后台绑定不随前台切换。共享 profile 编辑须显示受影响用途。 |
| 设计风格 | DESIGN.md 提供可修改的工程设计基线，Stitch 形成实际设计稿 | 色彩、字体、页面细节不是用户已确认品牌；按需求和实际兼容验证调整，无须逐像素审批。 |
| 记忆 / Agent | MemoryCore 第一外部候选，Pi / Cognee 按具体缺口评估 | 少量案例证明收益和生命周期后接入；不强制同时安装所有候选。 |
