## 1. 系统已实现（V65，勿重复建设）

| §20.14 步骤 | 实现 |
|---|---|
| 1. 单独同意并填写 | 同意页「紧急联系人」卡片；保存需 EMERGENCY_CONTACT 单独同意（SQL 内重验，缺省/撤回 fail-closed） |
| 2. 发送验证邀请 | `POST /emergency-contact/verify-start` 生成一次性 token（DB 只存 SHA-256，7 天有效）。Alpha 模拟：token 显示给用户手工转交，**无真实发送** |
| 3. 联系人明确接受 | `verify-confirm`：绑定验证时间/方式/条款版本，180 天有效期 |
| 4. 保存时间、方式、版本 | 行内 `verified_at / verified_method / consent_version` |
| 5. 变更或过期重新确认 | 变更联系方式即回 DRAFT；验证到期读取时惰性降回 DRAFT |
| 6. 未验证仅草稿 | DRAFT 状态无法用于任何联络决策；撤回为终态 |
| 联络规则之审计 | 每次读取存量行同事务写 `EMERGENCY_CONTACT_VIEW` 审计 |
| 加密存储 | 联系方式 AES-256-GCM 应用层加密（§17.4），密钥部署注入，SQL 永不见明文 |

## 2. Beta 联络规则（人工执行，系统不提供触发器）

联络紧急联系人是**人工决策 + 人工执行**，系统角色仅提供已验证联系方式：

1. 触发条件（全部满足，缺一不可）：
   - 经批准的 R4_IMMINENT 场景（B0-01 §3 已形成「联络」决定）；
   - 用户存有 **VERIFIED** 紧急联系人（DRAFT/过期/撤回一律不可用）；
   - 决定由安全责任人本人或其明示授权者作出并记录。
2. 执行：人工查看（本身留审计）→ 电话/短信联络 → 记录联系结果于 Case 台账。
3. 禁止事项：
   - 不由模型自动触发；不做任何形式的自动/半自动外呼；
   - 联系人回复**不写入**普通记忆或 Canonical Memory（§20.14）；
   - 误触发、无人接听、号码失效、用户申诉 → 分别按 §3 处置。
4. 每次查看、解密、联系均审计：系统读取审计已实现；人工电话联络由执行人
   在 Case 台账补记（时间、对象、结果）。

## 3. 异常处置

| 情形 | 处置 |
|---|---|
| 误触发（联络后发现非 R4） | 台账记录；向联系人与用户致歉说明；复盘规则误报来源 |
| 无人接听 | 按决定再试一次或转为平台内介入；记录尝试次数与时间 |
| 号码失效 | Case 标注；通过平台内渠道提示用户更新联系人（不自动降级验证状态） |
| 用户申诉被联络 | 走 B0-01 §5 申诉流程；隐私负责人 3 工作日内答复 |
