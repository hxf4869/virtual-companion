# 08 · 数据保留策略（草案 v1）

对应需求 §16.7「数据保留建议」、TODO R48「RETENTION」。**状态：Agent 代拟
草案，Owner/法务复核后生效。** §16.7 明确：具体周期需根据法律、平台和业务
确认；工程上只保证每类数据的周期在 `vc.data_retention_policy` 中**版本化**
（V70），运行时永远从表里读有效策略，不允许开发人员写死。

> ADR-0006 决定的 30 天对话正文周期只适用于 Owner-only 本地 dogfood，不替换本表的
> Beta 草案，也不批准将全部 DRAFT policy 置为 ACTIVE。

## 1. 机制（已实现）

- **策略表**：V104 为 `data_retention_policy` 增加显式
  `DRAFT/ACTIVE/RETIRED`；仓库 seed 全部为 DRAFT。runtime 无权直接改策略，且只能调用
  `run_retention_category`，该 wrapper 在每类执行前重读最新 ACTIVE 版本；没有 ACTIVE
  policy 时 fail-closed，不能绕过为任意 cutoff 删除。
- **dry-run 与统计**：调度开关默认 false；即便开启，`VC_RETENTION_DRY_RUN` 仍默认 true，
  只运行同一 legal-hold-aware 查询估算行数。每类计数/失败写入 `job_lease_run_history`；
  单类失败发 P1 `RETENTION_PURGE_FAILED`，不阻断其他类别。
- **Legal hold**：ACTIVE hold 可按 owner + 类别或 ALL 阻止 dry-run/purge；只有 HMAC
  owner context 下的 ACTIVE ADMIN/PRIVACY_OPERATOR 可设置或解除，动作保存固定 reason code
  与 actor/time，不保存自由文本案情。
- **备份删除传播**：V103 COMPLETED tombstone 保护在线 message/memory/vector/export；V104
  提供 migration-owner-only 的 digest manifest export/reconcile。恢复必须先 dry-run，再 apply，
  runtime 不能调用 apply；演练入口已覆盖“备份后删除、恢复旧备份、外部 manifest 再删除”。
- **开关**：Owner/法务未批准 policy 前保持 `VC_RETENTION_PURGE_ENABLED=false`；批准后先以
  `VC_RETENTION_DRY_RUN=true` 复核统计，只有再次签字才可显式设为 false。

## 2. 草案 v1 周期（待复核）

| 类别 | 覆盖存储 | 草案周期 | 说明 |
|---|---|---|---|
| NORMAL_CHAT | `vc.message`（含摘要失效联动） | 365 天 | 清理同事务内把覆盖被删消息的会话摘要置 invalid（FR-CHAT-004 规则的集合化） |
| DELETED_CHAT | —— | 30 天 | 当前删除即物理级联，无残留可清；策略行先行占位，函数恒返 0 |
| MEMORY_CANDIDATE | `memory_item` status=PENDING_CONFIRMATION | 90 天 | 仅未确认候选；证据与向量随行级联 |
| REJECTED_CANDIDATE | `memory_item` status=REJECTED | 30 天 | 同上 |
| MODEL_CALL_DETAIL | `provider_attempt` + `generation_route` | 180 天 | 模型调用明细与路由记录 |
| SAFETY_LOG | `safety_event` | 365 天 | 内容安全日志（无 FK 设计，独立清理） |
| EXPORT_RESIDUE | `export_request` 终态行 | 30 天 | 只清 READY/FAILED/EXPIRED；进行中的 PENDING 永不被清扫 |
| STREAM_FRAGMENT | `realtime_event` | 30 天 | 流式片段/持久事件 |

身份审计日志（identity_auth_event）沿用既有 180 天策略（V22/P2-03），
不在本表重复。备份保留周期归 BACKUP 任务（R47）。

## 3. 变更流程

1. Owner/法务确认新周期后，追加新 `policy_version`，先保持 `status=DRAFT`；
2. 在合成/副本环境以 dry-run 复核各类计数、legal hold 和单类失败隔离；
3. 审批记录完成后由 migrator 将新版本置 `ACTIVE`、旧版本置 `RETIRED`；
4. 生产先开启 scheduler + dry-run，复核 run history 后再单独批准真实 purge；
5. 备份/WAL 边界之外持续保存 digest tombstone manifest，任何恢复都先 dry-run reconcile。
