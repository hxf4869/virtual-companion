# V2 调度入口（Codex）

- 日期：2026-10-27
- 计划：`docs/planning/2026-10-27-v2-execution-plan.md`（每个工作项的内容、依赖与验收）
- 决策：`docs/decisions/0009-v2-sillytavern-host-direction.md`
- 进度：`TODO.md`「V2 执行序列」

本文件规定 V2 的分工、调度循环、工具调用方式与提示词模板。Codex 收到 Owner 的调度指令后从这里开始。

## 1. 分工

| 角色 | 执行者 | 职责 | 写入范围 |
|---|---|---|---|
| 调度者 | Codex | 选下一个工作项、派发、门禁检查、送审、回填进度、推送 | 只写 `TODO.md`「V2 执行序列」；不写业务代码、契约或计划 |
| 实施者 | 本机 zcode | 实现单个工作项、同步契约、验证、提交 | 该工作项范围内的代码、契约、迁移、生成物；W00 / W01 回填执行计划第 6 / 7 节；不改 `TODO.md` |
| 审计与规划者 | Claude Code | 每个工作项送审时审计；触发重新规划时调整计划 | 审计只读；规划只改执行计划与 ADR-0009 |
| Owner | 用户 | 运行配置、真机验收、真实外部动作授权、产品与架构重新决策 | — |

同一时间只有一个执行者写工作树：调度者在 zcode 或 Claude Code 运行期间不改文件、不提交。

## 2. 调度循环

### 2.0 开始前

1. 读 `AGENTS.override.md`、`AGENTS.md`、ADR-0009、执行计划第 1–5 节、本文件。
2. `git status` 除已知的未跟踪文件外无改动，`main` 与 `origin/main` 同步；否则停止并报告。
3. 确认两个工具可运行（第 3 节）；Codex 须以允许子进程访问网络与写工作树的权限运行，否则 zcode / Claude Code
   无法调用模型——此时停止并报告，不反复重试。
4. 读 `TODO.md`「V2 执行序列」，确定各项状态。

### 2.1 选择工作项

按编号顺序选第一个未完成且依赖满足的项。依赖满足指依赖项状态为 `DONE` 或 `READY_FOR_OWNER`。

| 项 | 依赖 | 项 | 依赖 |
|---|---|---|---|
| W00 | — | W09 | W03、W07 |
| W01 | W00 | W10 | W05、W09 |
| W02 | W00 | W11 | W09 |
| W03 | W00（结论为可行）、W01 | W12 | W03、W05 |
| W04 | W03 | W13 | W00、W12 |
| W05 | W00、W03 | W14 | W13 |
| W06 | W01、W05 | W15 | W04、W08、W10、W14 |
| W07 | W06 | W16 | W15 |
| W08 | W07 | | |

只缺 Owner 项（Stitch 稿、真实凭据、预算、目标手机、部署授权）时照常派发：实施者完成可用合成数据完成的部分，
缺 Owner 输入的子项记为 `BLOCKED`。没有可派发的项时停止并报告。

### 2.2 派发

1. 记录 `BASE=$(git rev-parse HEAD)`。
2. 用第 4.1 节模板生成实施提示词，按第 3.1 节调用 zcode，后台运行并等待结束。

### 2.3 门禁检查（调度者自己做，不改代码）

- zcode 已提交且推送，`git status` 干净；`BASE..HEAD` 的改动属于该工作项范围。
- 按 `AGENTS.md` 检查表，对受影响组件在 `HEAD` 上重跑一次验证入口，记录命令与结果。
- 实施汇报中的用例状态都给出了依据；未运行的没有报成 PASS。
- W00 / W01 已回填执行计划第 6 / 7 节。

不通过：把失败原因写进第 4.1 节“附加信息”，用 `-c` 续接 zcode 会话修复，然后重做门禁检查。

### 2.4 送审

门禁通过后，按第 4.2 节调用 Claude Code 审计 `BASE..HEAD`。根据输出最后一行处理：

- `VERDICT: PASS`：进入 2.5。
- `VERDICT: FIX_REQUIRED`：把发现原样交 zcode 修复（续接会话）→ 门禁检查 → 按第 4.3 节复核。
- `VERDICT: REPLAN`：按第 4.4 节调用规划；输出 `PLAN: UPDATED` 时按新计划重新选项，
  输出 `OWNER_DECISION_REQUIRED` 时停止并报告。

同一工作项累计 3 次修复续接后仍未通过门禁或复核，停止并报告。

### 2.5 回填与推进

在 `TODO.md` 对应条目下回填，提交（中文提交信息）并推送，然后回到 2.1：

```text
- [x] `V2-W00` ……（原文不改）
      结果：DONE（2026-10-28）；提交 <BASE>..<HEAD>；审计 PASS
      用例：C01 PASS；C02 NOT_RUN（原因）；……
```

状态规则：全部完成为 `DONE` 并勾选；代码完成但还差 Owner 人工验收为 `READY_FOR_OWNER`，不勾选；
只完成部分且被 Owner 输入阻塞为 `BLOCKED`，不勾选并写明缺什么。

### 2.6 停止并报告 Owner

出现以下任一情况时停止调度，向 Owner 报告当前项、已完成部分、阻塞原因与需要的决定：

- W00 结论为不可行，或规划输出 `OWNER_DECISION_REQUIRED`；
- 同一项 3 次修复后仍未通过；
- 下一步需要真实模型调用、真实邮件 / 飞书发送或远端部署，而本次会话没有授权；
- zcode 或 Claude Code 无法运行（未登录、权限、网络）；
- 没有可派发的项，或 W16 审计通过（输出 V2 完成总结）。

中断后用同一启动提示词重启 Codex 即可；状态以 `TODO.md` 与 Git 为准。重启时若仍有 zcode 进程在运行，先等待它结束。

## 3. 调用方式

日志放在仓库外，例如 `LOG_DIR=${TMPDIR:-/tmp}/vc-v2-dispatch`，不提交。提示词先写入文件再传入，避免引号转义问题。

### 3.1 zcode（实施）

zcode 不在 `PATH` 上，命令行入口在应用包内（0.17.0 实测路径；应用更新后若不存在，在
`/Applications/ZCode.app` 内查找 `zcode.cjs`）：

```bash
ZCODE=/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs
REPO=/Users/hxf/projects/virtual-companion
# 首次派发
nohup node "$ZCODE" -p "$(cat "$LOG_DIR/W00.prompt.txt")" --cwd "$REPO" \
  > "$LOG_DIR/W00.zcode.log" 2>&1 &
echo $! > "$LOG_DIR/W00.zcode.pid"
# 修复续接（同一仓库最近一次 zcode 会话）
nohup node "$ZCODE" -c -p "$(cat "$LOG_DIR/W00.fix1.prompt.txt")" --cwd "$REPO" \
  > "$LOG_DIR/W00.fix1.log" 2>&1 &
```

`--prompt` 默认使用完全放权模式（`yolo`）。一个工作项可能运行很久：后台运行，每隔几分钟用
`kill -0 $(cat …pid)` 检查是否结束，结束后读日志末尾的汇报。

### 3.2 Claude Code（审计与规划）

```bash
cd /Users/hxf/projects/virtual-companion
# 审计 / 复核：禁用写文件工具，可运行只读命令
claude -p "$(cat "$LOG_DIR/W00.audit.prompt.txt")" \
  --permission-mode bypassPermissions --disallowedTools "Edit Write NotebookEdit" \
  > "$LOG_DIR/W00.audit.log" 2>&1
# 规划：允许修改计划文件并提交
claude -p "$(cat "$LOG_DIR/W00.plan.prompt.txt")" --permission-mode bypassPermissions \
  > "$LOG_DIR/W00.plan.log" 2>&1
```

## 4. 提示词模板

`<…>` 由调度者替换。

### 4.1 实施（zcode）

```text
你是 virtual-companion V2 的实施者，执行 V2-<Wxx>。
1. 先读 AGENTS.md、docs/decisions/0009-v2-sillytavern-host-direction.md、
   docs/planning/2026-10-27-v2-execution-plan.md 第 1–4 节与 <Wxx> 小节，
   再读该小节列出的 docs/source/v2-r3/ 章节、相关代码与契约。
2. 只做 <Wxx> 的范围。契约、迁移、生成物与实现同项同步；新增依赖可直接引入，固定版本并登记许可。
3. 按 AGENTS.md 检查表做一次相称验证；不删测试、不加 skip、不削弱断言。
4. 小步提交，中文提交信息，提交后推送。不要修改 TODO.md。
5. W00 / W01 须回填执行计划第 6 / 7 节。
6. 不做真实模型调用、真实邮件 / 飞书发送或远端部署；运行配置缺失时用合成数据，把相关子项记为 BLOCKED。
7. 最终回复只用以下格式：
   结果：DONE | PARTIAL | BLOCKED
   提交：<hash 列表>
   验证：<命令> → PASS/FAIL（每条一行）
   用例：<ID> PASS/FAIL/NOT_RUN/BLOCKED/NOT_APPLICABLE —— 依据（每条一行）
   未完成与阻塞：……
   需要 Owner 的事项：……
附加信息（首次派发为空；修复时填门禁失败原因或审计发现）：
<…>
```

### 4.2 审计（Claude Code）

```text
你是 virtual-companion V2 的审计者。审计 V2-<Wxx>，提交范围 <BASE>..<HEAD>。
只读：不修改文件、不提交、不推送。验证结果以下方门禁记录为准，怀疑不实时才自行重跑相关命令。
依据：AGENTS.md、ADR-0009、执行计划第 3 节与 <Wxx> 小节、该小节列出的 docs/source/v2-r3/ 章节。
检查：
1. 范围：是否只做了 <Wxx>，交付是否完整；
2. 正确性与安全：给出具体缺陷（文件:行、触发条件、后果）；
3. 契约：catalog / OpenAPI / migration / RLS / 生成物与实现是否一致；
4. 验收：用例状态是否有证据，未运行的没有报成 PASS；
5. 计划：实现事实是否让后续工作项的计划假设失效。
只报告确认的问题；风格偏好不算发现。
FIX_REQUIRED 时逐条列出必须修复的发现（编号、文件:行、问题、期望）；REPLAN 时说明哪条计划假设不成立及证据。
最后一行固定为：VERDICT: PASS | FIX_REQUIRED | REPLAN
实施汇报：
<zcode 最终回复>
门禁记录：
<命令 → 结果>
```

### 4.3 复核（Claude Code）

```text
你是 virtual-companion V2 的审计者。复核 V2-<Wxx> 的审计发现修复，提交范围 <FIX_BASE>..<HEAD>。
只读。只核对下列发现是否已正确修复、修复是否引入新问题，不重做完整审计。
发现：
<上次 FIX_REQUIRED 的发现>
最后一行固定为：VERDICT: PASS | FIX_REQUIRED
```

### 4.4 规划调整（Claude Code）

```text
你是 virtual-companion V2 的规划者。V2-<Wxx> 触发重新规划：
<审计 REPLAN 说明或停止原因，附证据>
只调整 docs/planning/2026-10-27-v2-execution-plan.md 中受影响的工作项与依赖（必要时同步本调度入口的依赖表）。
如果需要改变 ADR-0009 §1–§2 的产品范围或架构，不要修改，说明可选方案并输出 OWNER_DECISION_REQUIRED。
修改后运行 git diff --check，中文提交并推送。
最后一行固定为：PLAN: UPDATED | OWNER_DECISION_REQUIRED
```
